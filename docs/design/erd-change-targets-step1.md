# 사고뭉치 이슈 5 기준 DB 변경 대상 검토표

기존 변경 대상 22개를 **이번에 구현한 항목 9개, 조장에게 확인할 항목 8개, 후속 기능으로 넘길 항목 5개**로 다시 분류했다. 기존 K01–K08·M01–M04·B01–B10 식별자를 유지해 앞선 검토와 연결한다. 유지·수정·보강은 변경의 성격이고, 아래 세 그룹은 이슈 #5에서의 실행 구분이다.

분류 기준은 [이슈 #5](https://github.com/SKNETWORKS-FAMILY-AICAMP/SKN34-FINAL-3TEAM/issues/5)의 ERD 검증과 세 서비스 DB 마이그레이션 범위다. 미확정 정책과 설계 의미가 충돌하는 항목은 조장에게 확인하고, 신규 기능 구조는 후속 이관안으로 분리한다. 9개 항목은 기존 스키마 범위에서 구현·검증했고, 나머지 13개에 대한 이관·정책 결정은 제안 상태다.

검토 기준은 2026-10-26 확인한 이슈 본문, develop 커밋 `5fbdebf25e53fdaefaae3f3d2ae26b1a5b3c22ad`, 요구사항 정의서 v0.5다. 클래스·시퀀스·상태 다이어그램도 대조했다. `feature/db-schema`에서 ERD의 타입·NULL·제약을 명확히 하고 3개 DB의 DDL을 작성했다. API·ORM·기능 코드와 시드 데이터는 추가하지 않았다. 검증 상세는 [DB 스키마 구현·검증](db-schema-validation.md)에 기록했다.

작업 중 추가된 develop `5fc1ab092defc97c85b2ddd98674961f8dfe9302`의 아키텍처 폴더 구조·클래스 문서 정리도 반영했다. ERD와 API 계약은 동일하며 아래 근거 행 번호는 최초 검토 기준 커밋을 따른다.

**이슈 진행 순서와 완료 판정**

1. 기존 ERD 전체와 API·상태·클래스·시퀀스 문서를 대조해 필드·상태·제약의 대응표를 작성한다. 새 다이어그램의 가정을 자동 확정 정책으로 승격하지 않는다.
2. 위 확인 항목을 조장에게 전달할 수 있는 질문으로 정리하고, 독립적인 기존 스키마 부분부터 작성한다. 확정된 설계 변경은 erd.md 및 관련 명세에 먼저 반영한다.
3. core·learning의 Flyway와 report의 수기 Alembic을 작성한다. 미결 항목이 DDL의 의미에 영향을 주면 해결 또는 이관 합의 전까지 전체 완료로 표시하지 않는다.
4. 빈 개발 DB에서 적용·제약·재실행·report 린트를 확인한다. 검증용 입력과 시드 납품을 구분하고, 공유 DB 볼륨을 임의 삭제하지 않는다.
5. PR에 변경 사유·기준 문서·확인된 결정·검증 결과를 정리한다. 이번 문서 업데이트만으로 이슈 완료 또는 기능 검증 완료라고 표시하지 않는다.
