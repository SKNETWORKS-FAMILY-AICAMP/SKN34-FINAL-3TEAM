# 이슈 #22 learning 미션 조회와 데모 미션 시드

작성일: 2026-10-27. 기준: `develop`의 `95c62e3` 및 [이슈 #22](https://github.com/SKNETWORKS-FAMILY-AICAMP/SKN34-FINAL-3TEAM/issues/22), [API 명세 2.2·3.8·4.1](../design/api-spec.md), [기능 명세 P03·FN-LRN-02·03](../design/functional-spec.md), [상태 다이어그램 3.1](../design/state-diagram.md), [기획서 5장](<../outputs/프로젝트_기획서_사고뭉치.pdf>).

learning-service의 `GET /internal/missions`, `GET /internal/missions/{id}`와 데모 미션 시드를 만들면서 정한 내용과 근거, 다른 이슈에서 검토할 점을 기록한다. API 계약과 데이터베이스 스키마는 바꾸지 않았다.

## 판정 API가 미션 질문을 받지 않는 문제

데모 미션의 예시 답과 아이 수준 답안을 실제 ai 판정(Claude, `judge@2`)으로 확인하다가 발견했다. 판정 요청([API 명세 4.2](../design/api-spec.md))에는 학생 답과 기준표 요소만 있고 미션 질문이 없다. 그래서 요소 설명이 "입장을 밝힘"처럼 일반적이면 주제와 무관한 답도 충족으로 판정된다.

| 대응 | 내용 | 결과 |
|---|---|---|
| 이번 시드 (A안) | 요소 설명에 미션 주제를 넣음. 예: "쉬는 시간을 20분으로 늘리는 것에 찬성 또는 반대 입장을 밝힘" | 주제와 무관한 답 7개 중 6개 `RETHINK`, 1개 `HELD`. 넣기 전에는 주제와 무관한 답도 충족으로 판정됨 |
| 근본 해결 (B안) | 판정 요청에 미션 질문을 추가 (api-spec 4.2, ai `judge@3`, learning 요청) | #25에서 결정 |

같은 확인에서 본 점:

- 예시 답은 AI 판정 대상 16문항 모두 `CORRECT`. 빠진 답(까닭 없음·관찰만·근거 평가 없음)은 `PARTIAL`.
- 풀이 단계에서 방법은 맞고 계산만 틀린 답은 AI가 `CORRECT`로 본다. 최종 답 규칙 판정이 오답으로 잡으므로, 두 결과를 합치는 방식은 #25에서 정한다.
- "방법 세우기" 설명이 "어떤 방법이든"처럼 넓으면 틀린 방법(뗀 부분을 잊고 큰 직사각형만 계산)도 충족이 된다. 설명을 "남은 부분만의 넓이를 구하는 방법"으로 좁혀 여러 방법은 인정하고 틀린 방법은 걸렀다.
- 같은 답이 실행마다 다르게 판정되는 경우가 있다(분석하기 서술의 잘못된 원인 답). 사람 검증(P11)에서 확인할 대상이다.

## 구현에서 정한 것

클래스·메서드 이름은 [클래스 다이어그램 4.1](../design/class-diagram.md)을 따른다 (`MissionController`, `MissionService.listForStudent(studentId, grade)`·`get(missionId)`, `MissionRepository`, `MissionView`).

| 항목 | 정한 내용 | 근거 |
|---|---|---|
| 학생용 객체 이름 | `MissionView`. 정답·예시 답·기준표 필드가 없어 응답에 섞일 수 없음 | class-diagram의 `get(missionId) MissionView`. `Mission`은 공개·검토 규칙을 가진 관리자 쪽 엔티티 이름으로 남김 |
| 수행 상태 조회 | `MissionRepository`가 `attempt`에서 미션별 가장 최근 시도를 읽음. 없으면 `NOT_STARTED` | class-diagram에서 `MissionService`는 `MissionRepository`만 쓰고 `AttemptService`가 `MissionService`를 씀. attempt 쪽 서비스를 부르면 순환 |
| 상세 조회 범위 | 목록과 같은 범위(공개 + 학생 학년·입력 방식). 비공개·범위 밖이면 `409 MISSION_NOT_AVAILABLE`, 없으면 `404 NOT_FOUND`. 메서드는 `get(missionId, grade)` | api-spec 1.3 `MISSION_NOT_AVAILABLE`(비공개·범위 밖 미션). 프론트 목업(`demoGateway.mission`)도 학생 학년 미션 안에서만 상세를 엶. 범위 확인에 학년이 필요해 class-diagram의 `get(missionId)`에 인자 하나 추가. 목업은 범위 밖을 `404 NOT_FOUND`로 처리해 api-spec과 다름 → 프론트 담당 확인 |
| 목록 위치 | `position`은 학생 학년 목록에서 1부터, `total`은 그 목록 크기. 페이지 나누기(api-spec 1.1)는 Controller | api-spec 3.8 목록 항목. Service 인자는 class-diagram 그대로 |
| 학생 확인 | `X-User-Role: STUDENT`이고 `X-Student-Scope`에 학생 1명일 때만 허용, 그 학생이 조회 대상. 아니면 `403 FORBIDDEN` | 학생 미션 API는 역할 학생 (api-spec 2.2). core가 `/missions`를 그대로 넘기는 프록시라 경로에 학생 ID가 없음 (api-spec 4.1) |
| 학년 | core가 쿼리 `grade`(3~6)로 넘김. 범위 밖이면 `400 VALIDATION_FAILED` | 학생 학년은 core에만 있음. 지원 학년 초3~6 (P03) |
| 응답 필드 | 프론트 `Mission` 모델 이름. 안내는 `hint`, 학년 범위는 `grade`·`gradeMax`, 입력 틀은 `inputTemplate`. 프론트의 `scene`은 DB에 없어 제외(장면은 `sceneUri`) | api-spec 3.7·3.8이 프론트 모델을 잠정 계약으로 씀 |
| 목록 봉투 | `PageResponse`를 `mission/controller`에 둠 | 공통으로 쓸 곳이 생기면 `_common`으로 옮김. architecture 2.6 `_common` 구성을 지금 바꾸지 않음 |
| 입력 방식 범위 | 학년으로 계산(논술은 초5 이상, P03). `inputTypes`는 받지 않음 | class-diagram의 `MissionController.list(grade, inputTypes)`와 `MissionService.listForStudent(studentId, grade)`가 다름. 입력 방식 범위를 넘기는 주체·기준이 문서에 없고 P03이 학년으로 정함 |

## #14와의 관계

#14(Repository 공통 기반·Testcontainers)는 아직 develop에 없고 작업 중이다. #22는 #14가 고치는 파일(`build.gradle.kts`, `application.yml`, `_common/persistence/`)을 건드리지 않고, #14 코드에도 기대지 않는다. Mapper는 UUID·jsonb를 문자열로 받아 Repository에서 변환한다. Mapper 인터페이스와 Repository 클래스를 나누는 #14 방식은 따른다.
