# 리텐션 확장: 생활공간·기념 액자·추억 검색 (2026-11-12)

「리텐션 서비스 확장 기획 공유안」 v0.3(2026-11-12)을 검토해 확정한 범위와 근거다. 설계 반영은 [기능명세 P27·FN-RET-09~13](../design/functional-spec.md#14-확정-정책), [유스케이스 UC-35·36](../design/usecase.md), [ERD 3.5.2·4.6](../design/erd.md), [상태 3.7](../design/state-diagram.md), [API 2.12·4.1.4·4.2.6](../design/api-spec.md), [아키텍처](../design/architecture.md)에 있다. 기능명세 요구사항 열의 "확장안 N.N"은 이 문서의 절 번호다. 12/7 데모 범위에 포함한다.

## 1. 범위

| 기능 | 내용 | 상태 |
|---|---|---|
| 생활공간 | 정적 방 1개, 고정 가구·캐릭터, 가구 스킨 교체 | 확정 |
| 기념 액자 | 테마 5개 문제 완료 시 회차당 1개 저장 | 확정 |
| 추억 앨범 | 보유 액자 회차 목록과 당시 기록 열람 | 확정 |
| 추억 검색 | 자연어 질문으로 본인 지난 기록 검색(pgvector, 미션 + 최종 답변) | 확정 |
| 추억 설명(RAG) | 검색 결과에 대한 짧은 설명, 버튼 클릭 시 1회 생성 | 확정 |

초기 범위 제외: 캐릭터 이동·가구 편집, 신규 가구, 기념 문장, 당시 캐릭터 모습 보존, 미완료 회차·진행 중 주차 표시, 추가 문제(EXTRA), 대화형 회상, 미니게임·자유 촬영

## 2. 공통 용어

- **회차**: 학생이 특정 주에 받은 테마 1회. 키 `(student_id, theme_id, theme_week_start)`
  - 별도 테이블 없이 `attempt`의 `theme_id`·`theme_week_start`로 식별(learning V11)
  - `student_id`는 서버가 인증 정보로 채우므로 API에는 `(theme_id, theme_week_start)`만 노출
  - 같은 테마가 다른 주에 재사용되면(P23) 다른 회차
- **진행 주 제외**: `theme_week_start < 이번 주`인 회차만 표시·검색

## 3. 기능별 내용

### 3.1 생활공간

화면
- 방 배경 위에 고정 가구와 캐릭터를 겹쳐 표시. 이동·격자·회전·편집 모드 없음
- 방 배경(벽지) = 학생이 착용 중인 기존 `BACKGROUND` 슬롯 아이템. 별도 방 배경 슬롯 없음
  - 착용한 배경 아이템이 없으면 기본 벽지 표시

| 가구 | 동작 |
|---|---|
| 학습 책상 | 주간 테마 화면으로 이동 |
| 추억의 벽 | 액자 슬롯 표시, 앨범 열기, 빈 슬롯에 액자 걸기 |
| 옷장 | 기존 꾸미기(`Customize`) + 가구 스킨 변경 |
| 그 외 장식(선택) | 스킨 교체만 |

캐릭터
- 기존 `Companion.tsx` SVG를 고정 위치에 표시하고 착용 모자·옷·소품을 겹쳐 그림
- 착용 아이템 렌더링은 현재 미구현(선택만 가능) → 신규 작업. 기존 홈 적용은 미결

가구 스킨
- 가구별 기본 스킨 무료 + 추가 스킨은 기존 포인트로 해금(즉시 차감·영구 소유·환급 없음, P22)
- 기존 기능 재사용: 해금 API(`POST /students/me/look-items/{itemKey}/unlock`), 포인트 원장, 슬롯별 착용 테이블(`student_look_equipment`), 아이템 목록 API
- 데이터 위치: 기존 아이템 테이블(`look_item`)의 `slot`에 가구 슬롯 추가(`DESK`, `WALL`, `WARDROBE`)
  - core 마이그레이션 1개(슬롯 CHECK 제약 변경, V35는 고치지 않음), 관리자 아이템 등록 화면 재사용
  - P22 "4개 슬롯(모자·옷·소품·배경)" 정책 개정
- 가구 1개 = 착용 슬롯 1개로 취급 → 가구당 스킨 1개 적용이 자동 보장

액자 슬롯
- 추억의 벽에 고정 슬롯 6개(기준안). core에 `학생 → 슬롯 번호 → 회차 키, 저장 시각` 저장
- 저장 시 learning에 본인 보유 액자인지 확인. 저장·취소 버튼 방식, 실패 시 편집 내용 유지

### 3.2 기념 액자

지급 기준
- 회차의 테마 5개 문제가 모두 완료되면 지급
- 프리미엄 일요일 완료, 자정 넘긴 이어하기 완료도 인정
- 주간 완주 포인트(토요일 마감, FN-RET-05)와 기준이 다름. 결과적으로 프리미엄은 획득 기회가 하루 더 있음
- 포인트 이벤트에 의존하지 않고 learning의 `attempt.completed_at`으로 직접 판정
  - 이유: 현재 learning이 `finished`·`completedOnDay`를 응답하지 않아 `THEME_FINISHED`가 발생하지 않는 것으로 추정(`WeeklyThemeService.kt`, learning #484 전)

저장(learning_db)
- `theme_frame(id, student_id, theme_id, theme_week_start, theme_version_id, awarded_at, seen_at, created_at)`
- 유일 제약 `(student_id, theme_id, theme_week_start)`
- `awarded_at` = 5개 문제 중 가장 늦은 `completed_at`, `seen_at` = 획득 안내 확인 시각(없으면 "새 액자")
- 이미지 = 테마 버전의 기존 intro/outro 이미지 또는 `ThemeArt` SVG

처리
- 지급: 시도 완료 처리와 같은 트랜잭션에서 `INSERT … ON CONFLICT DO NOTHING` → 실패 상태·재처리 불필요, 중복 없음
- 소급: 배포 시 기존 시도 기록으로 1회 배치. 재실행해도 결과 동일. 소급분은 `seen_at`을 채워 안내 일괄 노출 방지
- 판정 규칙이 바뀌어도 이미 저장된 액자는 유지

### 3.3 추억 앨범

목록
- 대상: 보유 액자 회차, 진행 주 제외, EXTRA 제외
- 정렬: 최근 회차순, 필터 없음
- 카드: 테마 이미지·제목, 회차 주, 획득일, 전시 여부, 새 액자 표시

상세
- 회차 내 5개 미션 → 기존 시도 상세(`StudentWorkPage.tsx`, 처음·보완 답변 비교) 재사용
- 엔딩·정답은 학생이 그 주 엔딩을 본 경우만 표시(`theme_story_view` OUTRO, P23)
- 판정 정정은 기존 정정 안내 그대로 표시

빈 상태
- 보유 액자 없음: 기능 안내 + "예시" 표시 액자

### 3.4 추억 검색

흐름
1. 앨범 상단 검색창에 질문 입력(예시 질문 칩 3개, 입력 예시임을 표시)
2. frontend → core(하루 한도 확인) → learning 검색 API
3. 검색 범위: 본인 보유 액자 회차의 테마 문제 시도, 진행 주 제외
4. 질문 임베딩: learning 임베딩 클라이언트(신규) → ai `/internal/embeddings`(`text-embedding-3-small`, 1536차원, #467 구현 완료)
5. 검색용 테이블에서 범위 필터 후 코사인 유사도 정렬
6. 회차 단위 카드 상위 3개 반환. 임계값 미만이면 "관련 결과 없음"
7. 카드 선택 → 앨범 상세

저장소
- ai 임베딩 API만 재사용. learning의 이전 `KnowledgeEmbedder`는 V17 정리에서 지워졌으므로 learning 임베딩 클라이언트를 새로 둠
- 교육과정 지식 테이블(`knowledge_chunk`)은 재사용하지 않음. learning_db에 검색용 테이블 신규 생성
- #463(2026-11-11) "미션·테마 생성에 벡터 검색 미사용" 결정은 그대로 유지. 추억 검색은 학생 기록 회상이라는 별도 용도로 pgvector를 씀

검색 대상: 완료 시도의 미션 + 학생 최종 답변
- 검색 문서 1건 = 테마 문제 완료 시도 1건(EXTRA 제외)
- 문서 내용: 테마 제목, 미션 장면·질문, 해당 시도의 최종 답변(`answer` 최신 버전의 `plain_text`)
- 답변이 짧아 나누지 않고 1건 = 벡터 1개
- 외부 전송 전 닉네임 마스킹, 이름·ID 미포함(3.6)
- "동물 집 만들었던 문제"(문제 주제)와 "내가 고양이 얘기 썼던 거"(답변 표현) 모두 검색 가능

테이블
- `memory_search_doc(id, attempt_id, student_id, theme_id, theme_week_start, content_text, embedding vector(1536), embedding_model, status, retry_count, lease_until, created_at, embedded_at)`
- `attempt_id` 유일 제약 → 시도당 문서 1건. 외래 키는 두되 CASCADE는 쓰지 않음(ERD 공통 규칙). 자녀 기록 삭제 시 `StudentDeletionService`의 삭제 순서에 넣어 시도보다 먼저 지움
- `status`: `PENDING`(반영 대기) / `PROCESSING`(임베딩 중) / `READY`(검색 가능) / `FAILED`(실패)
- 검색은 `READY`만 대상

생성 처리(완료 후 비동기)
1. 시도 완료 트랜잭션에서 `PENDING` 문서 행만 생성(임베딩 호출 없음 → 완료 응답 지연 없음)
2. learning 주기 작업이 `PENDING`을 64개 단위로 조건부 UPDATE(`PENDING → PROCESSING`, `lease_until` 기록)로 선점한 뒤 임베딩 호출 → `READY`
   - learning은 ShedLock을 쓰지 않음. 기존 `StuckJudgmentScheduler`처럼 조건부 UPDATE로 레플리카가 같은 행을 중복 처리하지 않게 함
3. 실패 시 `FAILED` + `retry_count` 증가, 주기 작업이 재시도. 한도 초과 건은 운영 확인 대상
4. `lease_until`이 지난 `PROCESSING`은 `PENDING`으로 되돌림(처리 중 Pod 종료 복구)
5. 기능 배포 시 기존 완료 시도로 `PENDING` 일괄 생성 → 같은 작업으로 적재
- 학생 답변은 수정되지 않으므로(FN-LRN-08/09) 갱신 처리 없음

화면 처리
- 반영 대기·실패 중인 기록도 앨범에서는 정상 열람(앨범은 `theme_frame` 기준)
- 검색 결과에서만 빠짐. 방금 완료한 기록이 검색되지 않을 수 있다는 안내는 빈 결과 화면에 표시

보조 검색
- `answer.plain_text` 키워드 검색(ILIKE)을 결과서의 비교 기준선으로 구현

결과서 대응
- 실제 임베딩 생성·pgvector 적재·검색·화면 연결, 추가·삭제 시 색인 반영 흐름(PENDING → READY, 삭제 순서)
- 평가 데이터: 가상 학생·자체 미션 합성 기록(AI Hub 원문 미사용)
- 접근 범위 시험: 다른 학생·진행 주·EXTRA·`READY` 아닌 문서 미포함 확인

### 3.5 추억 설명(RAG)

1. 검색 결과 화면의 "설명 보기" 클릭 시에만 호출
2. learning이 근거 구성(카드 최대 3개): 테마 제목, 미션 질문 요약, 최종 답변 일부, 회차 날짜. 근거는 `[1]~[3]` 번호로만 지칭
3. 근거 부족(최고 유사도 임계값 미만 또는 답변이 너무 짧음)이면 호출 없이 "설명할 기록이 충분하지 않음"
4. learning → ai 설명 API 호출. 2~3문장, 근거 외 활동 생성 금지, 감정·의도·능력 추정 금지, 근거 번호 표기
5. 출력 `{text, citations:[1,2]}`
6. learning 검증: 근거 번호 범위, 인용 문구의 원문 포함 여부. 실패 시 "설명 생성 실패"
7. 번호를 실제 회차·시도로 바꿔 반환
8. 실패해도 검색 카드는 유지, 정형 문장으로 대체하지 않음
9. 검색 질문·설명 응답은 저장하지 않음. 운영 로그에도 원문 미기록
10. 사용 모델: ai 서비스 기본 LLM 설정 재사용(별도 모델 설정 없음)

### 3.6 운영

개인정보
- 학생 답변의 외부 임베딩·LLM 전송은 기존 판정과 같은 기준으로 허용(NFR-SEC-03)
- 이름·학생·시도·답변 ID 미전송, 닉네임 마스킹(api-spec 4.2.1), 운영 로그 원문 미기록(NFR-SEC-05)
- 외부 전송 금지는 AI Hub 데이터(NFR-AIQ-02). 클러스터 내부 처리는 리포트 설명 sLLM에 한정된 결정(#473)

삭제
- learning `StudentDeletionService`에 액자·검색 문서 추가
- core `student.deleted` 처리에 액자 슬롯·추억 사용량 추가(가구 스킨 해금·착용은 기존 해금·착용 삭제에 포함)

무료/유료
- 생활공간·액자·앨범·스킨 해금: 무료/유료 동일(P13)
- 검색·설명: 하루 이용 한도만 적용(검색 20·설명 10, 무료·프리미엄 같음, `product.limits`, 2026-11-12 확정 9.1). core에 요청마다 1행 기록해 KST 하루 건수를 셈(`mission_daily_usage`와 같은 방식), 초과 시 `429 USAGE_LIMIT_REACHED`

리텐션 지표(DB 집계만)

| 지표 | 계산 |
|---|---|
| 액자 전시율 | 전시 슬롯 수 ÷ 보유 액자 수 |
| 액자 확인율 | `seen_at` 기록 액자 수 ÷ 보유 액자 수 |
| 전시까지 걸린 기간 | 슬롯 저장 시각 − `awarded_at` |
| 스킨 해금 수 | 원장 UNLOCK 중 가구 슬롯 건수 |
| 검색 이용 수 | 추억 사용량 기록 집계 |
| 다음 주 연속 참여 | 액자 보유 학생의 다음 주 테마 시도 여부 |

- 화면 이벤트가 필요한 지표(원문 열람률, 방문 기준 재방문)는 제외
- 결과서에 집계 기간·분모·대상 명시, 인과·학습 효과 주장 없음

## 4. 아키텍처 영향

- 새 서비스·Pod·네트워크 정책 없음. learning→ai, ai→LLM API는 이미 허용됨
- 벡터 저장은 기존 RDS learning_db. `vector` 확장은 이미 bootstrap으로 설치됨
- 통신 경로 2개 추가: 추억 검색(Web→core→learning→ai 임베딩), 추억 설명(Web→core→learning→ai LLM), 둘 다 동기 HTTP
- 타임아웃: ai LLM 호출(15초·재시도 1회) 때문에 learning→ai 설명은 35초가 필요해 core→learning 일반 프록시(30초)를 넘음 → 설명 경로는 별도 회로 `learning-memory`(core→learning 45초, 2026-11-12 확정). 검색은 임베딩 1회라 30초 안이며, ai 장애가 일반 프록시 회로로 번지지 않게 같은 `learning-memory` 회로를 씀(9.1)
- 비동기 임베딩은 RabbitMQ 이벤트 없이 learning 주기 작업으로 처리 → "learning은 발행 없음" 원칙 유지
- LLM 사용량 유형 추가: `MEMORY_EMBEDDING`, `MEMORY_EXPLANATION`(core `llm_usage.call_type` 마이그레이션 1개)
- 개인정보 범위: 추억 검색 임베딩·설명은 판정처럼 외부 LLM 사용. "학생 글이 클러스터 밖으로 나가지 않음"은 리포트 설명 sLLM 한정

### 9.2 learning 기념 액자·앨범 (#559, 2026-11-12)

learning V19 `theme_frame`과 내부 API 4개(api-spec 4.1.4 앨범 목록·회차 상세·확인·보유 확인)를 구현했다. 검색·설명은 별도 이슈다.

#### 9.2.1 확정한 결정 (담당자 확인 2026-11-12)

| 항목 | 결정 | 근거 |
|---|---|---|
| 소급 실행 | learning 기동 때마다 자동 실행(`app.theme-frame.backfill-on-startup`, 기본 켬) | 운영 작업이 따로 없고, 롤링 배포 중 이전 Pod가 처리한 완료도 다음 기동 때 채워짐. Flyway 데이터 마이그레이션은 마이그레이션 뒤 이전 Pod가 내려가기 전 완료분이 영영 빠짐 |
| 소급분 `seen_at` | `awarded_at`과 같은 값 | 결정적인 값이라 다시 돌려도 결과가 같음. `seen_at = awarded_at`인 행이 소급분이라 액자 확인율 집계(3.6) 때 걸러 낼 수 있음 |
| 진행 중인 주 제외 범위 | 내부 API 4개 모두(`theme_week_start < 이번 주 KST 월요일`) | 상세·확인은 404 `THEME_FRAME_NOT_FOUND`, 보유 확인에서 빠짐 → 추억의 벽(#555)에 앨범에 없는 액자가 걸리지 않음. 금요일에 받은 액자는 다음 주 월요일부터 보임 |
| 회차 상세 `attemptId` | 그 회차에서 그 문제를 마지막으로 학습 완료한 시도(토·일 다시 풀기 포함) | 기존 `/attempts/{id}/comparison`이 직전 마무리 시도와 비교해 처음 풀이와 다시 풀이를 함께 볼 수 있음 |

#### 9.2.2 구현 판단

- 엔딩 판정: #484 엔딩 상태(`WeeklyThemeService.ending`, 정답 고르기 기록과 그 금요일 문제 `THEME_REVIEW` 마무리로 계산)가 `ENDED`일 때만 회차 상세에 종료 이야기·정답을 담는다(P23). 이번 주 화면·종료 이야기 열람 허용과 같은 판정이라 앨범에서 엔딩 전 정답이 새지 않는다. 처음에는 #484 병합 전이라 `theme_story_view` OUTRO 열람 기록으로 정했다가, #484 병합(PR #569) 뒤 develop을 합치며 같은 판정으로 맞췄다. 정답을 고르지 않았거나 틀린 뒤 금요일 문제를 다시 마무리하지 않은 회차는 액자가 있어도 `ending.seen = false`다
- 완료 조건: 회차의 완료 시도(`THEME_DAY`·`THEME_REVIEW`, `completed_at` 있음)를 문제별로 묶어 테마 게시본(없으면 현재본)의 요일 문제 5개와 모두 맞으면 지급. 지급과 소급이 같은 SQL(`ThemeFrameMapper.completedRounds`)이라 결과가 같다. `EXTRA`는 회차 칸이 없어 자연히 빠진다(V12 CHECK)
- `awarded_at`: 문제별 처음 완료 시각 중 가장 늦은 값 = 다섯째 문제를 마친 순간. 프리미엄 일요일·자정 넘긴 이어하기 완료도 `completed_at` 그대로라 인정된다. 다시 풀기 완료는 UK 충돌로 무시돼 획득 시각·확인 상태가 바뀌지 않는다
- 동시 완료: 같은 회차의 서로 다른 두 문제 완료가 동시에 커밋되면 READ COMMITTED에서 서로의 완료를 못 봐 둘 다 지급을 건너뛸 수 있다. 판정 전에 회차 단위 `pg_advisory_xact_lock`을 잡아 차례로 판정한다(트랜잭션 끝에 풀림). `ThemeFrameConcurrencyTest`가 첫 트랜잭션 커밋 전 둘째가 잠금을 기다리고 커밋 뒤 액자 1개가 생기는 것을 확인한다. 놓친 회차가 있어도 다음 기동 소급이 채운다
- 버전 고정: `theme_version_id`는 지급 때 게시본. 이후 재게시와 무관하게 앨범 제목·그림·문제 목록이 유지된다. 지급 뒤 규칙이 바뀌어도 저장된 액자는 지우지 않는다(3.2)
- 그림: 시작 이야기 그림(`intro_image_uri`) presigned URL. 종료 그림은 엔딩 내용이라 쓰지 않고, 없으면 null(화면이 `ThemeArt`로 그림)
- 범위 검사: `X-Student-Scope`에 경로 학생이 없으면 403(api-spec 4.1.4). 역할은 보지 않고 core 프록시가 학생 본인 STUDENT 세션으로 부른다
- 삭제: `StudentDeletionService`의 한 트랜잭션에 `theme_frame` 물리 삭제를 더했다. 시도를 참조하지 않아 순서 제약이 없고 FK는 NO ACTION(CASCADE 없음)
- 학습 완료 응답은 바뀌지 않는다. 지급은 같은 트랜잭션의 부수 효과이고 서비스 간 호출·이벤트가 없다(시퀀스 3.8)

#### 9.2.3 한계

- 소급은 Pod가 뜰 때마다 시도 표 전체를 한 번 묶어 본다. 데모 규모에서는 가볍지만 기록이 크게 늘면 1회 실행 표식이나 관리 명령으로 바꾼다
- 도입 전 회차라도 그 뒤 테마가 다른 문제로 재게시됐으면 현재 게시본 요일 문제와 맞지 않아 소급되지 않는다(시도에 테마 버전이 없음)
- 검색 문서(`memory_search_doc`) 등록은 이 이슈 범위가 아니다(3.4 별도 이슈)

### 9.3 ai 추억 임베딩 구분·추억 설명 API (#565, 2026-11-12)

## 10. core 가구 스킨·추억의 벽 액자 슬롯 구현 (#555, 2026-11-12)

core V47 `V47__room_furniture_skins_and_frame_slots.sql`로 가구 슬롯 CHECK 확장과 `room_frame_slot`을 만들고, `GET`·`PUT /students/me/room/frame-slots`와 `equipped` 가구 슬롯을 구현했다(api-spec 2.10·2.12, ERD 3.5.1). learning 보유 확인은 #559 계약(api-spec 4.1.4)을 쓰며, core 시험은 그 계약대로 응답하는 가짜 HTTP 서버로 확인했다. 9장은 #559·#566이 쓰는 절이라 이 절을 따로 둔다.

### 10.1 확정한 결정 (담당자 확인 2026-11-12)

| 항목 | 결정 | 근거 |
|---|---|---|
| 가구 기본 스킨 | 기준안대로 행 없음. 착용 행이 없는 가구 슬롯(`equipped`의 null)이 기본 스킨이고 항상 고를 수 있음. 관리자는 추가 스킨만 등록 | 테마 `lake`·기본 벽지와 같은 방식이라 새 해금 경로·시드·가격 0 예외(`price_points > 0` CHECK)가 필요 없음 |
| 액자 슬롯 수 | 기준안대로 6개(`slot_no` 1~6 CHECK) | 설계 문서 전부가 쓰는 값 |
| 슬롯 조회의 제목·그림 | core가 learning 앨범 목록으로 채움(api-spec 2.12 계약 그대로) | 그림은 만료되는 presigned URL이라 core에 저장할 수 없음. web(#556) MSW 목과 계약이 바뀌지 않음. 대신 슬롯이 있으면 조회도 learning에 의존 |
| `equipped` 변경 방식 | 보낸 슬롯만 교체, 보내지 않은 슬롯은 유지(이전: 보내면 네 슬롯 전체 교체) | 기존 꾸미기 화면이 캐릭터 네 슬롯만 보내도 가구 스킨이 벗겨지지 않고 옷장 화면은 가구 슬롯만 보낼 수 있음. 이전 계약이 네 키를 모두 요구했으므로 캐릭터 슬롯 동작은 같음 |
| 커뮤니티 작성자 `look` | 캐릭터 네 슬롯만 | 가구는 본인 방에서만 보이며 커뮤니티 응답 모양을 바꾸지 않음 |

### 10.2 구현 판단

- 해금·착용: `LookCatalog`에 가구 슬롯 3개를 더했을 뿐 `LookUnlockService`·`StudentLookService`·원장 흐름은 그대로라 가구 스킨도 즉시 차감·`Idempotency-Key` 재전송·원장 UK·잔액 행 잠금으로 한 번만 차감되고, 잠긴 스킨은 409 `LOOK_LOCKED`, 다른 슬롯 아이템은 422다. 검사에 하나라도 걸리면 아무 슬롯도 바꾸지 않는다
- 액자 슬롯 저장 순서: 요청 검사(422, learning 호출 없음) → learning `frames/ownership`(미보유 404 `THEME_FRAME_NOT_FOUND`) → learning 앨범 목록(제목·그림) → 한 트랜잭션에서 학생 행 `FOR NO KEY UPDATE` 잠금 뒤 전체 삭제·삽입. learning을 기다리는 동안 DB 잠금을 잡지 않고, learning 단계가 실패하면 아무것도 저장하지 않아 화면이 편집 내용을 유지한다(3.1)
- 학생 행 잠금: 같은 학생의 저장 두 개가 겹쳐도 삭제·삽입이 PK 충돌 없이 차례로 반영되고, 삭제 확정(학생 상태 변경)과도 직렬화된다. 삭제가 먼저 끝났으면 409 `STUDENT_UNAVAILABLE`
- 서킷: 보유 확인·앨범 목록은 ai를 부르지 않는 learning DB 조회라 일반 `learning-json`을 쓴다. 설계(클래스 3.7)의 `LearningMemoryClient`는 #566의 `learning-memory`(ai 장애 격리용) 전용으로 두고 `room/client/LearningFrameClient`를 따로 만들었다
- 앨범 조회: `size=100`으로 앞쪽부터 걸린 회차를 모두 찾을 때까지 읽는다. 걸린 액자가 없으면 learning을 부르지 않는다. 앨범에 없는 회차(보통 없음)는 조회 응답에서 빼고 로그를 남긴다
- `theme_week_start`는 DB CHECK로 월요일만 받는다(learning `theme_week_start`와 같은 값, 요청 단계에서는 422)
- 삭제: `StudentLookService.clear`(학생 삭제 확정 트랜잭션)에서 포인트·해금·착용 다음에 `room_frame_slot`을 지운다. 가구 스킨 해금·착용은 기존 해금·착용 삭제에 들어 있다(3.6)

### 10.3 한계·병합 메모

- 마이그레이션 번호: #566(PR #572)이 V46으로 먼저 병합돼 이 작업은 V47이다(gitops 로컬 core 리비전 `v47`)
- 학생이 액자를 많이 가지면(100개 초과) 조회 때 앨범을 여러 쪽 읽는다. 데모 규모에서는 한 쪽이며, 커지면 learning에 회차 키로 제목·그림을 주는 경로를 더한다
- 리텐션 지표(3.6) "전시까지 걸린 기간"은 `room_frame_slot.saved_at − awarded_at`이다. 전체 교체여도 계속 걸려 있는 액자는 슬롯을 옮겨도 처음 건 시각을 유지하고, 내렸다가 다시 걸면 다시 건 시각이 된다

## 11. core 추억 앨범 공개 프록시 (#560, 2026-11-12)

학생 공개 앨범 3경로(api-spec 2.12)를 learning 4.1.4 앨범 경로(#559)로 넘기고, 목록 `displayed`를 추억의 벽 슬롯(`room_frame_slot`, #555)으로 채운다. #555(PR #575)·#559(PR #571) 병합 뒤 develop 기준이다. 9장(#559·#566)·10장(#555)과 겹치지 않게 절을 따로 둔다.

### 11.1 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| `displayed` 처리 순서 | #555 슬롯 테이블을 바로 읽어 채움(테이블이 없을 때의 "항상 false" 단계 없음) | #555 구현이 먼저 있어 임시 값을 두면 web(#561)이 잘못된 전시 표시를 받는 기간만 생김 |
| `displayed` 기준 | 지금 `room_frame_slot`에 같은 `(theme_id, theme_week_start)` 행이 있으면 true | 슬롯 저장 때 learning 보유를 확인했으므로 core 행만으로 판정 가능, learning 추가 호출 없음 |
| 서킷 | 일반 `learning-json`(응답 30초) | 이슈 지침. ai를 부르지 않는 DB 조회라 `learning-memory`로 격리할 이유 없음(#555 `LearningFrameClient`와 같음). 5장 표의 `learning-memory` 회로는 검색·설명에만 해당 |
| 쿼리 | `page`·`size`만 다시 만들어 넘기고 범위 검사는 learning | 다른 쿼리(예 `studentId`)를 learning에 흘리지 않음. 범위 기준을 한 곳(learning 4.1.4)에 둠 |
| 오류 | learning 400·404 `THEME_FRAME_NOT_FOUND`·5xx를 그대로 전달. learning 200 본문이 앨범 모양이 아니면 502 `LEARNING_CONTRACT_INVALID` | 이슈 지침(오류 코드 그대로). 깨진 본문에 `displayed`를 붙일 수 없으므로 #555와 같은 계약 오류 코드 사용 |
| 클라이언트 위치 | 기존 `LearningMemoryClient`에 앨범 메서드를 두고 일반 `LearningClient`를 주입 | 클래스 3.7 설계(앨범은 `MemoryProxyService`→`LearningMemoryClient`)를 따르면서 서킷만 `learning-json` |

### 11.2 기준안 값

새 기준안 값 없음. 페이지 기본 20·최대 100은 learning 4.1.4 값을 그대로 쓰고 core는 다시 정하지 않는다.

### 11.3 한계·병합 메모

- core 시험은 병합된 learning 4.1.4 계약(`MemoryController`·learning OpenAPI `AlbumPage`·`AlbumRound`)대로 응답하는 가짜 HTTP 서버로 확인했다. 실제 learning과의 연동은 배포 환경에서 확인한다
- 목록은 learning 응답을 한 번 파싱해 다시 직렬화하므로 learning이 칸을 더하면 그대로 전달되지만 숫자·문자열 표기(예 소수 자릿수)는 Jackson 기본 직렬화를 따른다
