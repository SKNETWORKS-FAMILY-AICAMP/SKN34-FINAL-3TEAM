# 리텐션 확장: 생활공간·기념 액자·추억 검색 (2026-11-12)

「리텐션 서비스 확장 기획 공유안」 v0.3(2026-11-12)을 검토해 확정한 범위와 근거다. 설계 반영은 [기능명세 P27·FN-RET-09~13](../design/functional-spec.md#14-확정-정책), [유스케이스 UC-35·36](../design/usecase.md), [ERD 3.5.2·4.6](../design/erd.md), [상태 3.7](../design/state-diagram.md), [API 2.12·4.1.4·4.2.6](../design/api-spec.md), [아키텍처](../design/architecture.md)에 있다. 기능명세 요구사항 열의 "확장안 N.N"은 이 문서의 절 번호다. 12/7 데모 범위에 포함한다.

## 1. 범위

| 기능 | 내용 | 상태 |
|---|---|---|
| 생활공간 | 정적 방 1개, 고정 가구·캐릭터, 가구 스킨 교체 | 확정 |
| 기념 액자 | 테마 5개 문제 완료 시 회차당 1개 저장 | 확정 |
| 추억 앨범 | 보유 액자 회차 목록과 당시 기록 열람 | 확정 |
| 추억 검색 | 자연어 질문으로 본인 지난 기록 검색(pgvector, 미션 + 최종 답변) | 확정 |
| 추억 설명(RAG) | 검색 결과에 대한 짧은 설명, 버튼 클릭 시 1회 생성 | 확정 |

초기 범위 제외: 캐릭터 이동·가구 편집, 신규 가구, 기념 문장, 당시 캐릭터 모습 보존, 미완료 회차·진행 중 주차 표시, 추가 문제(EXTRA), 대화형 회상, 미니게임·자유 촬영

## 2. 공통 용어

- **회차**: 학생이 특정 주에 받은 테마 1회. 키 `(student_id, theme_id, theme_week_start)`
  - 별도 테이블 없이 `attempt`의 `theme_id`·`theme_week_start`로 식별(learning V11)
  - `student_id`는 서버가 인증 정보로 채우므로 API에는 `(theme_id, theme_week_start)`만 노출
  - 같은 테마가 다른 주에 재사용되면(P23) 다른 회차
- **진행 주 제외**: `theme_week_start < 이번 주`인 회차만 표시·검색

## 3. 기능별 내용

### 3.1 생활공간

화면
- 방 배경 위에 고정 가구와 캐릭터를 겹쳐 표시. 이동·격자·회전·편집 모드 없음
- 방 배경(벽지) = 학생이 착용 중인 기존 `BACKGROUND` 슬롯 아이템. 별도 방 배경 슬롯 없음
  - 착용한 배경 아이템이 없으면 기본 벽지 표시

| 가구 | 동작 |
|---|---|
| 학습 책상 | 주간 테마 화면으로 이동 |
| 추억의 벽 | 액자 슬롯 표시, 앨범 열기, 빈 슬롯에 액자 걸기 |
| 옷장 | 기존 꾸미기(`Customize`) + 가구 스킨 변경 |
| 그 외 장식(선택) | 스킨 교체만 |

캐릭터
- 기존 `Companion.tsx` SVG를 고정 위치에 표시하고 착용 모자·옷·소품을 겹쳐 그림
- 착용 아이템 렌더링은 현재 미구현(선택만 가능) → 신규 작업. 기존 홈 적용은 미결

가구 스킨
- 가구별 기본 스킨 무료 + 추가 스킨은 기존 포인트로 해금(즉시 차감·영구 소유·환급 없음, P22)
- 기존 기능 재사용: 해금 API(`POST /students/me/look-items/{itemKey}/unlock`), 포인트 원장, 슬롯별 착용 테이블(`student_look_equipment`), 아이템 목록 API
- 데이터 위치: 기존 아이템 테이블(`look_item`)의 `slot`에 가구 슬롯 추가(`DESK`, `WALL`, `WARDROBE`)
  - core 마이그레이션 1개(슬롯 CHECK 제약 변경, V35는 고치지 않음), 관리자 아이템 등록 화면 재사용
  - P22 "4개 슬롯(모자·옷·소품·배경)" 정책 개정
- 가구 1개 = 착용 슬롯 1개로 취급 → 가구당 스킨 1개 적용이 자동 보장

액자 슬롯
- 추억의 벽에 고정 슬롯 6개(기준안). core에 `학생 → 슬롯 번호 → 회차 키, 저장 시각` 저장
- 저장 시 learning에 본인 보유 액자인지 확인. 저장·취소 버튼 방식, 실패 시 편집 내용 유지

### 3.2 기념 액자

지급 기준
- 회차의 테마 5개 문제가 모두 완료되면 지급
- 프리미엄 일요일 완료, 자정 넘긴 이어하기 완료도 인정
- 주간 완주 포인트(토요일 마감, FN-RET-05)와 기준이 다름. 결과적으로 프리미엄은 획득 기회가 하루 더 있음
- 포인트 이벤트에 의존하지 않고 learning의 `attempt.completed_at`으로 직접 판정
  - 이유: 현재 learning이 `finished`·`completedOnDay`를 응답하지 않아 `THEME_FINISHED`가 발생하지 않는 것으로 추정(`WeeklyThemeService.kt`, learning #484 전)

저장(learning_db)
- `theme_frame(id, student_id, theme_id, theme_week_start, theme_version_id, awarded_at, seen_at, created_at)`
- 유일 제약 `(student_id, theme_id, theme_week_start)`
- `awarded_at` = 5개 문제 중 가장 늦은 `completed_at`, `seen_at` = 획득 안내 확인 시각(없으면 "새 액자")
- 이미지 = 테마 버전의 기존 intro/outro 이미지 또는 `ThemeArt` SVG

처리
- 지급: 시도 완료 처리와 같은 트랜잭션에서 `INSERT … ON CONFLICT DO NOTHING` → 실패 상태·재처리 불필요, 중복 없음
- 소급: 배포 시 기존 시도 기록으로 1회 배치. 재실행해도 결과 동일. 소급분은 `seen_at`을 채워 안내 일괄 노출 방지
- 판정 규칙이 바뀌어도 이미 저장된 액자는 유지

### 3.3 추억 앨범

목록
- 대상: 보유 액자 회차, 진행 주 제외, EXTRA 제외
- 정렬: 최근 회차순, 필터 없음
- 카드: 테마 이미지·제목, 회차 주, 획득일, 전시 여부, 새 액자 표시

상세
- 회차 내 5개 미션 → 기존 시도 상세(`StudentWorkPage.tsx`, 처음·보완 답변 비교) 재사용
- 엔딩·정답은 학생이 그 주 엔딩을 본 경우만 표시(`theme_story_view` OUTRO, P23)
- 판정 정정은 기존 정정 안내 그대로 표시

빈 상태
- 보유 액자 없음: 기능 안내 + "예시" 표시 액자

### 3.4 추억 검색

흐름
1. 앨범 상단 검색창에 질문 입력(예시 질문 칩 3개, 입력 예시임을 표시)
2. frontend → core(하루 한도 확인) → learning 검색 API
3. 검색 범위: 본인 보유 액자 회차의 테마 문제 시도, 진행 주 제외
4. 질의 변환(2026-11-16 추가, 16장): learning → ai `/internal/memory-queries`가 질문을 핵심 키워드·기간·검색용 문장으로 바꿈. 실패하면 원문 질문으로 진행
5. 질문 임베딩: learning 임베딩 클라이언트(신규) → ai `/internal/embeddings`(`text-embedding-3-small`, 1536차원, #467 구현 완료). 변환 성공이면 검색용 문장, 실패면 원문을 임베딩
6. 검색용 테이블에서 범위·기간 필터 후 벡터(코사인 유사도 임계값 이상)·키워드(ILIKE) 순위를 RRF로 합침
7. 회차 단위 카드 상위 3개 반환. 벡터·키워드 모두 걸린 것이 없으면 "관련 결과 없음"
8. 카드 선택 → 앨범 상세

저장소
- ai 임베딩 API만 재사용. learning의 이전 `KnowledgeEmbedder`는 V17 정리에서 지워졌으므로 learning 임베딩 클라이언트를 새로 둠
- 교육과정 지식 테이블(`knowledge_chunk`)은 재사용하지 않음. learning_db에 검색용 테이블 신규 생성
- #463(2026-11-11) "미션·테마 생성에 벡터 검색 미사용" 결정은 그대로 유지. 추억 검색은 학생 기록 회상이라는 별도 용도로 pgvector를 씀

검색 대상: 완료 시도의 미션 + 학생 최종 답변
- 검색 문서 1건 = 테마 문제 완료 시도 1건(EXTRA 제외)
- 문서 내용: 테마 제목, 미션 장면·질문, 해당 시도의 최종 답변(`answer` 최신 버전의 `plain_text`)
- 답변이 짧아 나누지 않고 1건 = 벡터 1개
- 외부 전송 전 닉네임 마스킹, 이름·ID 미포함(3.6)
- "동물 집 만들었던 문제"(문제 주제)와 "내가 고양이 얘기 썼던 거"(답변 표현) 모두 검색 가능

테이블
- `memory_search_doc(id, attempt_id, student_id, theme_id, theme_week_start, content_text, embedding vector(1536), embedding_model, status, retry_count, lease_until, created_at, embedded_at)`
- `attempt_id` 유일 제약 → 시도당 문서 1건. 외래 키는 두되 CASCADE는 쓰지 않음(ERD 공통 규칙). 자녀 기록 삭제 시 `StudentDeletionService`의 삭제 순서에 넣어 시도보다 먼저 지움
- `status`: `PENDING`(반영 대기) / `PROCESSING`(임베딩 중) / `READY`(검색 가능) / `FAILED`(실패)
- 검색은 `READY`만 대상

생성 처리(완료 후 비동기)
1. 시도 완료 트랜잭션에서 `PENDING` 문서 행만 생성(임베딩 호출 없음 → 완료 응답 지연 없음)
2. learning 주기 작업이 `PENDING`을 64개 단위로 조건부 UPDATE(`PENDING → PROCESSING`, `lease_until` 기록)로 선점한 뒤 임베딩 호출 → `READY`
   - learning은 ShedLock을 쓰지 않음. 기존 `StuckJudgmentScheduler`처럼 조건부 UPDATE로 레플리카가 같은 행을 중복 처리하지 않게 함
3. 실패 시 `FAILED` + `retry_count` 증가, 주기 작업이 재시도. 한도 초과 건은 운영 확인 대상
4. `lease_until`이 지난 `PROCESSING`은 `PENDING`으로 되돌림(처리 중 Pod 종료 복구)
5. 기능 배포 시 기존 완료 시도로 `PENDING` 일괄 생성 → 같은 작업으로 적재
- 학생 답변은 수정되지 않으므로(FN-LRN-08/09) 갱신 처리 없음

화면 처리
- 반영 대기·실패 중인 기록도 앨범에서는 정상 열람(앨범은 `theme_frame` 기준)
- 검색 결과에서만 빠짐. 방금 완료한 기록이 검색되지 않을 수 있다는 안내는 빈 결과 화면에 표시

키워드 검색
- 2026-11-16 변경(멘토 피드백, #679): 키워드 검색을 비교 기준선에서 하이브리드 검색의 한 축으로 바꿈. 변환 키워드로 `memory_search_doc.content_text`를 ILIKE 검색해 벡터 순위와 합침(16장)
- #563이 구현한 `answer.plain_text` ILIKE는 결과서의 키워드 단독 비교 기준선으로 그대로 둠

결과서 대응
- 실제 임베딩 생성·pgvector 적재·검색·화면 연결, 추가·삭제 시 색인 반영 흐름(PENDING → READY, 삭제 순서)
- 평가 데이터: 가상 학생·자체 미션 합성 기록(AI Hub 원문 미사용)
- 접근 범위 시험: 다른 학생·진행 주·EXTRA·`READY` 아닌 문서 미포함 확인
- 검색 방식 비교(#568): 키워드 단독·벡터 단독·하이브리드를 같은 평가셋·접근 범위로 비교하고 질의 변환 LLM 비용·지연을 함께 기록(16장)

### 3.5 추억 설명(RAG)

1. 검색 결과 화면의 "설명 보기" 클릭 시에만 호출
2. learning이 근거 구성(카드 최대 3개): 테마 제목, 미션 질문 요약, 최종 답변 일부, 회차 날짜. 근거는 `[1]~[3]` 번호로만 지칭
3. 근거 부족(최고 유사도 임계값 미만 또는 답변이 너무 짧음)이면 호출 없이 "설명할 기록이 충분하지 않음"
4. learning → ai 설명 API 호출. 2~3문장, 근거 외 활동 생성 금지, 감정·의도·능력 추정 금지, 근거 번호 표기
5. 출력 `{text, citations:[1,2]}`
6. learning 검증: 근거 번호 범위, 인용 문구의 원문 포함 여부. 실패 시 "설명 생성 실패"
7. 번호를 실제 회차·시도로 바꿔 반환
8. 실패해도 검색 카드는 유지, 정형 문장으로 대체하지 않음
9. 검색 질문·설명 응답은 저장하지 않음. 운영 로그에도 원문 미기록
10. 사용 모델: ai 서비스 기본 LLM 설정 재사용(별도 모델 설정 없음)

### 3.6 운영

개인정보
- 학생 답변의 외부 임베딩·LLM 전송은 기존 판정과 같은 기준으로 허용(NFR-SEC-03)
- 이름·학생·시도·답변 ID 미전송, 닉네임 마스킹(api-spec 4.2.1), 운영 로그 원문 미기록(NFR-SEC-05)
- 외부 전송 금지는 AI Hub 데이터(NFR-AIQ-02). 클러스터 내부 처리는 리포트 설명 sLLM에 한정된 결정(#473)

삭제
- learning `StudentDeletionService`에 액자·검색 문서 추가
- core `student.deleted` 처리에 액자 슬롯·추억 사용량 추가(가구 스킨 해금·착용은 기존 해금·착용 삭제에 포함)

무료/유료
- 생활공간·액자·앨범·스킨 해금: 무료/유료 동일(P13)
- 검색·설명: 하루 이용 한도만 적용(검색 20·설명 10, 무료·프리미엄 같음, `product.limits`, 2026-11-12 확정 9.1). core에 요청마다 1행 기록해 KST 하루 건수를 셈(`mission_daily_usage`와 같은 방식), 초과 시 `429 USAGE_LIMIT_REACHED`

리텐션 지표(DB 집계만)

| 지표 | 계산 |
|---|---|
| 액자 전시율 | 전시 슬롯 수 ÷ 보유 액자 수 |
| 액자 확인율 | `seen_at` 기록 액자 수 ÷ 보유 액자 수 |
| 전시까지 걸린 기간 | 슬롯 저장 시각 − `awarded_at` |
| 스킨 해금 수 | 원장 UNLOCK 중 가구 슬롯 건수 |
| 검색 이용 수 | 추억 사용량 기록 집계 |
| 다음 주 연속 참여 | 액자 보유 학생의 다음 주 테마 시도 여부 |

- 화면 이벤트가 필요한 지표(원문 열람률, 방문 기준 재방문)는 제외
- 결과서에 집계 기간·분모·대상 명시, 인과·학습 효과 주장 없음
- 집계 SQL은 [`scripts/retention_metrics/`](../../scripts/retention_metrics/README.md)(#628, 15장)

#### 3.7.1 착용 그림 연결 (#455·#557, 2026-11-13)

착용 그림이 아직 없어 연결부만 먼저 넣었다. 그림을 만들면 파일만 넣으면 되고 코드는 고치지 않는다.

| 할 일 | 위치·방법 |
|---|---|
| 그림 파일 넣기 | `frontend/web/public/student-assets/` 아래에 그림 키와 같은 경로로. 예: 그림 키 `looks/hat-acorn.svg` → `public/student-assets/looks/hat-acorn.svg` |
| 파일 규칙 | 영문 소문자·숫자·`-`·`_`, 확장자 `svg`·`png`·`webp`(다른 형식·폴더 밖 경로는 그리지 않음, `roomAssets.ts` `wearAssetUrl`). 정사각형, 가로 60 기준으로 그림 |
| 위치·크기 | 그림 한가운데가 위 기준점에 놓이고 크기는 60 × 배율. 어긋나면 `roomAssets.ts` `WEAR_ANCHORS`의 그 캐릭터·칸 값만 고친다 |
| 아이템 등록 | 관리자 꾸미기 아이템 "그림 키"에 같은 경로(`looks/…`)를 넣는다(목업 아이템은 `looks/hat-acorn.svg`·`looks/outfit-rain.svg`·`looks/acc-lens.svg`) |
| 그리는 곳 | `Companion`의 `worn`(착용 칸 → 그림 키). 생각 지도·내 방·답변 작성·꾸미기 미리보기에서 학생 본인 캐릭터에 씀. 친구 생각 작성자 캐릭터도 응답 `author.look.equipped`로 그림(#635, 3.7.2) |
| 그리는 순서 | 옷 → 모자 → 소품(뒤가 위). 파일이 없거나 못 읽으면 그 칸만 빠지고 나머지는 그대로 |

## 4. 아키텍처 영향

- 새 서비스·Pod·네트워크 정책 없음. learning→ai, ai→LLM API는 이미 허용됨
- 벡터 저장은 기존 RDS learning_db. `vector` 확장은 이미 bootstrap으로 설치됨
- 통신 경로 2개 추가: 추억 검색(Web→core→learning→ai 임베딩), 추억 설명(Web→core→learning→ai LLM), 둘 다 동기 HTTP
- 타임아웃: ai LLM 호출(15초·재시도 1회) 때문에 learning→ai 설명은 35초가 필요해 core→learning 일반 프록시(30초)를 넘음 → 설명 경로는 별도 회로 `learning-memory`(core→learning 45초, 2026-11-12 확정). 검색은 질의 변환 8초 + 임베딩 20초라 30초 안이며(16장), ai 장애가 일반 프록시 회로로 번지지 않게 같은 `learning-memory` 회로를 씀(9.1)
- 비동기 임베딩은 RabbitMQ 이벤트 없이 learning 주기 작업으로 처리 → "learning은 발행 없음" 원칙 유지
- LLM 사용량 유형 추가: `MEMORY_EMBEDDING`, `MEMORY_EXPLANATION`(core `llm_usage.call_type` 마이그레이션 1개). 질의 변환 `MEMORY_QUERY`는 2026-11-16 추가(core 마이그레이션 1개 더, 16장)
- 개인정보 범위: 추억 검색 임베딩·설명은 판정처럼 외부 LLM 사용. "학생 글이 클러스터 밖으로 나가지 않음"은 리포트 설명 sLLM 한정

### 9.2 learning 기념 액자·앨범 (#559, 2026-11-12)

learning V19 `theme_frame`과 내부 API 4개(api-spec 4.1.4 앨범 목록·회차 상세·확인·보유 확인)를 구현했다. 검색·설명은 별도 이슈다.

#### 9.2.1 확정한 결정 (담당자 확인 2026-11-12)

| 항목 | 결정 | 근거 |
|---|---|---|
| 소급 실행 | learning 기동 때마다 자동 실행(`app.theme-frame.backfill-on-startup`, 기본 켬) | 운영 작업이 따로 없고, 롤링 배포 중 이전 Pod가 처리한 완료도 다음 기동 때 채워짐. Flyway 데이터 마이그레이션은 마이그레이션 뒤 이전 Pod가 내려가기 전 완료분이 영영 빠짐 |
| 소급분 `seen_at` | `awarded_at`과 같은 값 | 결정적인 값이라 다시 돌려도 결과가 같음. `seen_at = awarded_at`인 행이 소급분이라 액자 확인율 집계(3.6) 때 걸러 낼 수 있음 |
| 진행 중인 주 제외 범위 | 내부 API 4개 모두(`theme_week_start < 이번 주 KST 월요일`) | 상세·확인은 404 `THEME_FRAME_NOT_FOUND`, 보유 확인에서 빠짐 → 추억의 벽(#555)에 앨범에 없는 액자가 걸리지 않음. 금요일에 받은 액자는 다음 주 월요일부터 보임 |
| 회차 상세 `attemptId` | 그 회차에서 그 문제를 마지막으로 학습 완료한 시도(토·일 다시 풀기 포함) | 기존 `/attempts/{id}/comparison`이 직전 마무리 시도와 비교해 처음 풀이와 다시 풀이를 함께 볼 수 있음 |

#### 9.2.2 구현 판단

- 엔딩 판정: #484 엔딩 상태(`WeeklyThemeService.ending`, 정답 고르기 기록과 그 금요일 문제 `THEME_REVIEW` 마무리로 계산)가 `ENDED`일 때만 회차 상세에 종료 이야기·정답을 담는다(P23). 이번 주 화면·종료 이야기 열람 허용과 같은 판정이라 앨범에서 엔딩 전 정답이 새지 않는다. 처음에는 #484 병합 전이라 `theme_story_view` OUTRO 열람 기록으로 정했다가, #484 병합(PR #569) 뒤 develop을 합치며 같은 판정으로 맞췄다. 정답을 고르지 않았거나 틀린 뒤 금요일 문제를 다시 마무리하지 않은 회차는 액자가 있어도 `ending.seen = false`다
- 완료 조건: 회차의 완료 시도(`THEME_DAY`·`THEME_REVIEW`, `completed_at` 있음)를 문제별로 묶어 테마 게시본(없으면 현재본)의 요일 문제 5개와 모두 맞으면 지급. 지급과 소급이 같은 SQL(`ThemeFrameMapper.completedRounds`)이라 결과가 같다. `EXTRA`는 회차 칸이 없어 자연히 빠진다(V12 CHECK)
- `awarded_at`: 문제별 처음 완료 시각 중 가장 늦은 값 = 다섯째 문제를 마친 순간. 프리미엄 일요일·자정 넘긴 이어하기 완료도 `completed_at` 그대로라 인정된다. 다시 풀기 완료는 UK 충돌로 무시돼 획득 시각·확인 상태가 바뀌지 않는다
- 동시 완료: 같은 회차의 서로 다른 두 문제 완료가 동시에 커밋되면 READ COMMITTED에서 서로의 완료를 못 봐 둘 다 지급을 건너뛸 수 있다. 판정 전에 회차 단위 `pg_advisory_xact_lock`을 잡아 차례로 판정한다(트랜잭션 끝에 풀림). `ThemeFrameConcurrencyTest`가 첫 트랜잭션 커밋 전 둘째가 잠금을 기다리고 커밋 뒤 액자 1개가 생기는 것을 확인한다. 놓친 회차가 있어도 다음 기동 소급이 채운다
- 버전 고정: `theme_version_id`는 지급 때 게시본. 이후 재게시와 무관하게 앨범 제목·그림·문제 목록이 유지된다. 지급 뒤 규칙이 바뀌어도 저장된 액자는 지우지 않는다(3.2)
- 그림: 시작 이야기 그림(`intro_image_uri`) presigned URL. 종료 그림은 엔딩 내용이라 쓰지 않고, 없으면 null(화면이 `ThemeArt`로 그림)
- 범위 검사: `X-Student-Scope`에 경로 학생이 없으면 403(api-spec 4.1.4). 역할은 보지 않고 core 프록시가 학생 본인 STUDENT 세션으로 부른다
- 삭제: `StudentDeletionService`의 한 트랜잭션에 `theme_frame` 물리 삭제를 더했다. 시도를 참조하지 않아 순서 제약이 없고 FK는 NO ACTION(CASCADE 없음)
- 학습 완료 응답은 바뀌지 않는다. 지급은 같은 트랜잭션의 부수 효과이고 서비스 간 호출·이벤트가 없다(시퀀스 3.8)

#### 9.2.3 한계

- 소급은 Pod가 뜰 때마다 시도 표 전체를 한 번 묶어 본다. 데모 규모에서는 가볍지만 기록이 크게 늘면 1회 실행 표식이나 관리 명령으로 바꾼다
- 도입 전 회차라도 그 뒤 테마가 다른 문제로 재게시됐으면 현재 게시본 요일 문제와 맞지 않아 소급되지 않는다(시도에 테마 버전이 없음)
- 검색 문서(`memory_search_doc`) 등록은 이 이슈 범위가 아니다(3.4 별도 이슈)

## 10. core 가구 스킨·추억의 벽 액자 슬롯 구현 (#555, 2026-11-12)

core V47 `V47__room_furniture_skins_and_frame_slots.sql`로 가구 슬롯 CHECK 확장과 `room_frame_slot`을 만들고, `GET`·`PUT /students/me/room/frame-slots`와 `equipped` 가구 슬롯을 구현했다(api-spec 2.10·2.12, ERD 3.5.1). learning 보유 확인은 #559 계약(api-spec 4.1.4)을 쓰며, core 시험은 그 계약대로 응답하는 가짜 HTTP 서버로 확인했다. 9장은 #559·#566이 쓰는 절이라 이 절을 따로 둔다.

### 10.1 확정한 결정 (담당자 확인 2026-11-12)

| 항목 | 결정 | 근거 |
|---|---|---|
| 가구 기본 스킨 | 기준안대로 행 없음. 착용 행이 없는 가구 슬롯(`equipped`의 null)이 기본 스킨이고 항상 고를 수 있음. 관리자는 추가 스킨만 등록 | 테마 `lake`·기본 벽지와 같은 방식이라 새 해금 경로·시드·가격 0 예외(`price_points > 0` CHECK)가 필요 없음 |
| 액자 슬롯 수 | 기준안대로 6개(`slot_no` 1~6 CHECK) | 설계 문서 전부가 쓰는 값 |
| 슬롯 조회의 제목·그림 | core가 learning 앨범 목록으로 채움(api-spec 2.12 계약 그대로) | 그림은 만료되는 presigned URL이라 core에 저장할 수 없음. web(#556) MSW 목과 계약이 바뀌지 않음. 대신 슬롯이 있으면 조회도 learning에 의존 |
| `equipped` 변경 방식 | 보낸 슬롯만 교체, 보내지 않은 슬롯은 유지(이전: 보내면 네 슬롯 전체 교체) | 기존 꾸미기 화면이 캐릭터 네 슬롯만 보내도 가구 스킨이 벗겨지지 않고 옷장 화면은 가구 슬롯만 보낼 수 있음. 이전 계약이 네 키를 모두 요구했으므로 캐릭터 슬롯 동작은 같음 |
| 커뮤니티 작성자 `look` | 캐릭터 네 슬롯만 | 가구는 본인 방에서만 보이며 커뮤니티 응답 모양을 바꾸지 않음. 2026-11-16 친구 방 구경(20절, #708)에서는 가구 스킨도 보인다. 커뮤니티 목록 응답 모양은 그대로 |

### 10.2 구현 판단

- 해금·착용: `LookCatalog`에 가구 슬롯 3개를 더했을 뿐 `LookUnlockService`·`StudentLookService`·원장 흐름은 그대로라 가구 스킨도 즉시 차감·`Idempotency-Key` 재전송·원장 UK·잔액 행 잠금으로 한 번만 차감되고, 잠긴 스킨은 409 `LOOK_LOCKED`, 다른 슬롯 아이템은 422다. 검사에 하나라도 걸리면 아무 슬롯도 바꾸지 않는다
- 액자 슬롯 저장 순서: 요청 검사(422, learning 호출 없음) → learning `frames/ownership`(미보유 404 `THEME_FRAME_NOT_FOUND`) → learning 앨범 목록(제목·그림) → 한 트랜잭션에서 학생 행 `FOR NO KEY UPDATE` 잠금 뒤 전체 삭제·삽입. learning을 기다리는 동안 DB 잠금을 잡지 않고, learning 단계가 실패하면 아무것도 저장하지 않아 화면이 편집 내용을 유지한다(3.1)
- 학생 행 잠금: 같은 학생의 저장 두 개가 겹쳐도 삭제·삽입이 PK 충돌 없이 차례로 반영되고, 삭제 확정(학생 상태 변경)과도 직렬화된다. 삭제가 먼저 끝났으면 409 `STUDENT_UNAVAILABLE`
- 서킷: 보유 확인·앨범 목록은 ai를 부르지 않는 learning DB 조회라 일반 `learning-json`을 쓴다. 설계(클래스 3.7)의 `LearningMemoryClient`는 #566의 `learning-memory`(ai 장애 격리용) 전용으로 두고 `room/client/LearningFrameClient`를 따로 만들었다
- 앨범 조회: `size=100`으로 앞쪽부터 걸린 회차를 모두 찾을 때까지 읽는다. 걸린 액자가 없으면 learning을 부르지 않는다. 앨범에 없는 회차(보통 없음)는 조회 응답에서 빼고 로그를 남긴다
- `theme_week_start`는 DB CHECK로 월요일만 받는다(learning `theme_week_start`와 같은 값, 요청 단계에서는 422)

### 12.5 실제 외부 모델 추가 검증 (2026-11-12)

구현 커밋 `7f85fad5`와 병합된 #565 AI 서비스를 사용했다. 로컬 AI 서비스의 제공자를 OpenAI로 설정하고 `text-embedding-3-small`의 1536차원 벡터를 실제로 요청했다. 실제 학생 데이터 대신 합성 글만 전송했으며, 운영 DB와 AWS 서버는 사용하지 않았다.

- `MemorySearchTest`: 13건 통과, 실패·제외 0. 이 중 외부 연동 시험 1건은 실제 learning 클라이언트 → AI HTTP API(`purpose=MEMORY`) → OpenAI → pgvector READY 저장 → 질문 임베딩 → 해당 시도 검색까지 검증했다. 나머지 시험은 기존 DB·고정 벡터 검증이다.
- 외부 연동 1건의 임베딩·저장·질문 검색 소요 시간: 1,004ms. 브라우저 응답 시간이나 운영 부하 성능을 의미하지 않는다.
- 별도 의미 검색 점검: 합성 기록 12개(도서관·환경·친구·과학·수학·안전 각 2개), 관련 질문 8개와 무관 질문 2개. 실제 임베딩으로 문서 코사인 순위를 계산했다. 이 점검은 회차 묶음·권한을 포함하는 DB API 시험과 구분한다.
- 관련 질문의 예상 주제 문서가 1위인 경우: 7/8. 무관 질문은 2/2 모두 초기 기준값 0.35 미만이었다. 작은 합성 표본이므로 서비스 정확도로 일반화하지 않는다.
- 실패 예: “강에 사는 생물을 지키기 위해 한 일”은 하천 쓰레기 관련 문서를 찾지 못했고 최고 유사도도 0.269로 기준값 미만이었다. 기준값을 이 예시에 맞춰 임의로 낮추지 않았다.
- 문서 12개 일괄 임베딩 HTTP: 1,288.4ms. 질문 10개의 개별 임베딩 HTTP: 142.2~211.7ms. 전체 검색 응답 시간과 구분한다.
- 로컬 재현 증거: 실행 로그·JUnit XML·합성 질문별 순위 결과를 보관했다. API 키는 문서·커밋에 포함하지 않았다.

실제 외부 모델 연동은 가능하며 통과했다. 관련도 기준 최종 조정과 키워드 기준선 대비 개선 평가는 #568 대표 평가셋으로 별도 수행해야 한다. 이번 실행에서는 RabbitMQ 사용량 이벤트 전달을 검증하지 않았다.

### 12.8 임베딩 묶음 저장 성공 건수 정합성 (#563 후속, 2026-11-16)

- 기준: develop `d6535ecc`. `MemoryEmbeddingWorker.runBatch()`가 트랜잭션 안에서 외부 변수 `ready`를 증가시켜, 묶음 저장이 롤백돼도 반환 건수에 남는 문제를 수정했다.
- 수정 전 재현: 일회용 PostgreSQL에서 문서 2건 중 두 번째 저장에 예외를 주입했다. 실제 상태는 READY 0건·FAILED 2건인데 반환값은 1이었다. AI 호출은 테스트 대역이며 실제 외부 모델 시험과 구분한다.
- 수정: 묶음별 READY 갱신 건수를 `TransactionTemplate.execute` 안에서 계산하고, 해당 실행이 커밋을 마치고 반환한 뒤에만 전체 건수에 더한다. 앞 묶음의 커밋은 유지하고 롤백된 묶음은 합산하지 않는다.
- 영향: 운영 호출자인 `MemoryEmbeddingScheduler.tick()`은 반환 건수를 사용하지 않는다. 사용자 검색 결과·포인트·사용량 변경이 아니라 내부 반환값의 정합성 수정이다. API·DB 구조·묶음 크기·주기·재시도·트랜잭션 경계·삭제/리스 보호 조건은 그대로다.
- 회귀 사례: 묶음 중간 저장 실패, 첫 묶음 성공 후 다음 묶음 실패, 커밋 직전 실패, 여러 묶음 정상 처리, 임베딩 중 삭제로 READY 갱신 0건. 실패 사례는 다음 실행에서 재시도해 커밋된 건수와 반환값을 대조한다.

- 검증: JDK 21·일회용 pgvector PostgreSQL에서 추억 기능 65건 중 63건 통과, 기존 외부 AI 환경변수 조건부 시험 2건 건너뜀. 최초 실행에서 격리 사본의 성취기준 시드 파일 누락으로 액자 시험 9건이 기동 실패했고, 기존 `db/seed`를 복사해 해당 9건을 재실행하여 모두 통과했다. 추가 회귀 5건은 전부 통과했다. `bootJar`와 `git diff --check`도 통과했다. 실제 외부 모델·AWS 시험은 이번 집계 수정 범위 밖이다.

## 13. learning 추억 설명 구현 (#564, 2026-11-12)

- #563의 검색 문서와 액자 범위를 재사용한다. 새 테이블·마이그레이션 없음.

- 길이 미달이면 외부 호출 없이 INSUFFICIENT다. 길이 충족 시에는 관련도 재확인을 위해 질의 임베딩을 1회 호출하며, 관련도 미달일 때 생략하는 것은 설명 LLM 호출이다. 질문·검색 결과를 저장하지 않는 계약을 유지한다.

- 유효 근거 최고 유사도 0.35 이상(#563과 같은 `MEMORY_MINIMUM_SIMILARITY`). 확정 품질 평가는 #568에 연결한다. 유효 근거 없음·기준 미달·같은 모델 문서 없음은 INSUFFICIENT.
- 테마 제목 200자·미션 질문 앞부분 2,000자·답변 앞부분 2,000자로 제한한다. 요약 모델을 추가 호출하지 않는다. 닉네임·UUID를 먼저 가리고 번호만 전달한다.
- 응답의 문장별 근거 번호·인용을 실제 보낸 근거와 대조하고 번호를 회차·시도로 바꾼다. 인용 불일치·ai 422·502는 설명만 FAILED, 정형 문장 대체 없음. ai 장애(503·시간 초과·연결 실패)는 13.1에 따라 503.
- 35초 처리 예산에서 프로필·임베딩 소요를 빼고 남은 시간을 생성 HTTP에 전달한다. 클라이언트 재시도 없음. core의 기존 45초 설명 경로를 사용한다.
- 질문·설명 저장 및 원문 로그 없음. 실제 모델과 로컬 DB 통합 결과는 13.2~13.6(이전 `issue-564-memory-explanation.md`를 합침, #663).

### 13.1 ai 장애 때 설명 한도 미차감 (#592, 2026-11-12)

kind 확인 D(에픽 #562)에서 ai 0대일 때 learning이 질의 임베딩 실패를 200 `FAILED`로 돌려주고 core가 설명 1회를 센 것을 발견. 9.1 "장애로 학생 한도가 깎이지 않게"와 어긋나 learning 판정을 바꿈.

| 항목 | 결정 | 근거 |
|---|---|---|
| 고칠 곳 | learning이 장애를 503 `AI_UNAVAILABLE`로 구분, core 9.1 규칙(5xx 되돌림)은 그대로 | core는 이미 5xx면 되돌림. 검색 임베딩 장애(503)와 같은 방식이라 화면도 같은 안내를 쓸 수 있음. core가 `FAILED`를 모두 되돌리면 LLM 비용을 실제로 쓴 실패도 한도 밖이 됨 |
| 503(미차감) | 생성 전 실패: 프로필 조회·질의 임베딩 실패(검색과 같음), 생성 호출 전 35초 예산 소진. 생성 호출: ai 503·502 밖 5xx·시간 초과·연결 실패·learning ai 서킷 열림 | 생성이 일어나지 않았거나 시스템 장애로 결과를 받지 못함 |
| 200 `FAILED`(차감) | ai 422 인용 거부·502 형식 밖 응답·계약 밖 본문, learning 인용 검사 실패, ai 응답 뒤 예산 초과, 호출 중 근거 삭제·변경 | 생성이 실제로 일어난 결과. 반복 요청으로 LLM 비용이 한도 밖에서 늘지 않게 함 |
| 계약 | learning-service.yaml 설명 경로에 503 추가, core-service.yaml 설명 503 설명 보강, api-spec 2.12·4.1.4 | 응답 모양 변경 없음(새 칸 없음) |
| 화면(#567) | 설명 503은 검색 503과 같이 "잠시 뒤 다시" 안내, 남은 횟수 줄지 않음. `FAILED`는 "설명을 만들지 못했어요"(1회 사용) | 화면 구현 전이라 #567에서 반영 |

검증: learning `MemoryExplanationTest`(임베딩·프로필 실패 503, 생성 ai 503·시간 초과·연결 실패·서킷 열림 503, ai 502·422·계약 밖·인용 검사 실패 FAILED), core `MemoryProxyIntegrationTest`(설명 503 전달·되돌림). kind(2026-11-12)에서는 이 브랜치 learning을 Service에 붙지 않는 임시 파드(날짜 11/16, 주기 작업·메시지 소비 끔)와 ai 대역으로 띄워 직접 호출: 임베딩 503·생성 503 → 503 `AI_UNAVAILABLE`, 생성 502·422 → 200 `FAILED`, 정상 → `GENERATED`. 공유 ai·learning 배포와 실제 LLM·임베딩은 쓰지 않았고, core 경유 되돌림은 kind D의 검색 503 확인과 core 시험으로 갈음.

7. 임베딩 후와 생성 후에 범위·근거 내용을 재조회한다. 도중 삭제·변경되면 생성 결과를 반환하지 않는다.

### 15.2 구현 판단

- 기간: KST 날짜 구간 `[from, to)` 하나를 회차 주·해금 시각·검색 사용 날짜에 같이 쓴다. 기준일 `as_of`(기본 KST 오늘)가 속한 주는 진행 주라 액자 지표에서 뺀다(앨범·추억의 벽에 안 보임, 9.2.1)
- 확인율·전시까지 걸린 기간은 소급분(`seen_at = awarded_at`, 9.2.1)을 빼고 뺀 수를 메모로 낸다. 소급분은 확인 화면을 거치지 않았고 `awarded_at`이 도입 전 시각이라 두 지표를 왜곡한다. 전시율 분모에는 넣는다(보유는 사실)
- 전시율·전시까지 걸린 기간은 실행 시점에 걸린 슬롯 기준이다. 슬롯 변경 이력이 없어 기간 중 걸었다가 내린 액자는 셀 수 없다(10.3 `saved_at` 규칙 그대로)
- 다음 주 참여는 회차 단위로, 다음 주가 기준일 전에 끝난 회차만 판정하고 나머지는 보류로 따로 센다. 시도가 하나라도 있으면(진행 중 포함) 참여다
- 스킨 해금 수는 원장 `UNLOCK`의 사건 키(`itemKey` = `look_item.code`)를 `look_item.slot`과 맞춰 가구 슬롯만 센다. 검색 이용 수는 core 사용량 행이라 장애로 되돌린 요청(9.1)은 빠진다. 설명 사용량은 참고로 함께 낸다
- 1단계 JSON에는 학생 UUID만 있고 이름·닉네임·계정·답변은 없다. 결과 파일은 집계 뒤 지운다

### 15.3 kind 대조 (2026-11-13, 읽기 전용)

`kind-sagomungchi-local` `platform/postgres-0`에서 세션을 `default_transaction_read_only=on`으로 열고 두 파일을 실행한 뒤, 같은 세션 방식으로 원본 행을 직접 조회해 맞췄다. kind 데이터·컨테이너는 바꾸거나 멈추지 않았다. kind 학생 13명(시험 계정, `is_demo` 전원 false)은 모두 이전 확인용 시험 데이터라 아래 값은 SQL 검증용이며 지표 해석 대상이 아니다. 이전 확인이 날짜를 11/16로 둔 파드로 기록을 만들어 원본 시각이 실제 날짜(11/13)보다 뒤이므로 `as_of`를 정해 실행했다.

실행 조건: `from=2026-11-09`, `to=2026-11-23`, 대상 11명(삭제 확정 2명 제외, 시연·목록 제외 0명)

| # | 지표 | `as_of=2026-11-16` | `as_of=2026-11-23` | 원본 행 대조 |
|---|---|---|---|---|
| 1 | 액자 전시율 | 1/3 (33.3%) | 1/3 | `theme_frame` 11/9 주 3행(학생 3명), `room_frame_slot` 1행이 그중 1개와 회차 키 일치. 맞지 않는 슬롯 0 |

| 3 | 전시까지 걸린 기간 | 1건, 61.1시간 | 같음 | 걸린 액자 `saved_at` 11/15 15:07:02 − `awarded_at` 11/13 02:00:41(UTC) = 61시간 6분 |

- 필수 변수(`to`)가 없으면 안내만 출력하고 쿼리를 실행하지 않았다

### 15.4 한계

- `include_demo`는 kind에 시연 표식 학생이 없어 제외 0명으로만 확인했다. AWS 시연 DB(#601 재가동 뒤)에서는 기본값이면 대상이 0명이 되므로 시연 확인에는 `include_demo=1`을 쓴다

- 지표는 기술 통계이며 기능의 인과·학습 효과를 주장하지 않는다(NFR-OPS-06)

## 16. 추억 검색 질의 변환·하이브리드 (#679, 2026-11-16)

### 16.1 변경 이유
멘토 피드백(2026-11-16): "동물들이 살 수 있게 만들었던 문제 찾아줘" 같은 자연어 검색은 문맥·키워드 변환이 필요함. 질문 원문 임베딩만으로는 "찾아줘" 같은 요청 표현까지 의미에 섞이고 같은 기록만 반복해 걸려 품질이 기대보다 낮음. 3.4 "키워드 검색은 비교 기준선" 결정을 바꿔 질의 변환 + 벡터·키워드·기간 하이브리드 검색으로 보완함. 공개 API(api-spec 2.12)·웹 화면(#567)·하루 한도(검색 20회)는 그대로임.

### 16.2 흐름
1. learning이 질문을 마스킹(3.6)한 뒤 ai `POST /internal/memory-queries` `{query, today}` 호출
2. ai 기본 LLM 1회 → `{keywords, period, searchText}`
3. learning이 `searchText`를 임베딩(변환 실패면 원문)
4. 같은 접근 범위에서 벡터 검색(유사도 0.35 이상)과 키워드 검색(ILIKE)을 각각 하고 기간 필터를 둘 다에 적용
5. 두 순위를 RRF(k=60)로 합쳐 회차 단위 상위 3
6. 변환 실패(시간 초과·5xx·형식 밖 응답·서킷 열림·기능 꺼짐)면 키워드·기간 없이 원문 벡터 검색 = 변경 전과 같은 동작. 검색 자체는 실패시키지 않음. 임베딩 실패만 지금처럼 503 `AI_UNAVAILABLE`

### 16.3 기준안 (담당자 확인 2026-11-16)

| 항목 | 결정 |
|---|---|
| ai 내부 API | `POST /internal/memory-queries` `{query, today}` → `{keywords:[최대 5], period:{from,to}\|null, searchText, versions}`(api-spec 4.2.7). 질문은 learning이 마스킹한 뒤 전송 |
| 모델·시간 | ai 기본 LLM, 출력 상한 512토큰, ai LLM 호출 7초·재시도 없음(호출별 덮어쓰기), learning→ai 8초·재시도 없음(2026-11-16 실측으로 256토큰·4초·5초에서 변경, 16.7), learning 서킷 `ai-memory-query` |
| 시간 예산 | core→learning 검색 30초 > 변환 8초 + 임베딩 20초 + DB 처리 |
| 프롬프트 | 이름 `memoryQuery`, 승인 scope `ai/memory-query`, 내장 버전 `memory-query@1` |
| 가짜 구현 | `MEMORY_QUERY_PROVIDER=fake`: 공백 분리 키워드(앞 5개), 기간 없음, `searchText`=원문, 사용량 없음 |
| 사용량 | 새 `callType` `MEMORY_QUERY`(core `llm_usage` CHECK·`CallType`·OpenAPI·이벤트 스키마·ai/scoring 발행 목록, #680). ai는 #680 병합 뒤에만 발행 |
| 키워드 검색 | 같은 접근 범위(본인·보유 액자·지난 주·`READY`)의 `memory_search_doc.content_text`(테마 제목·미션·최종 답변) ILIKE, 키워드 중 하나 이상 일치. `%`·`_`는 이스케이프. 순위는 일치 키워드 수 내림차순, 같으면 최근 회차 |
| 기간 필터 | 반열림 구간 `[from, to)`. learning이 `to`를 이번 주 월요일(KST) 이하로 자르고 `from < to`가 아니면 기간을 버림. 회차 주 `[theme_week_start, +7일)`이 기간과 겹치는 문서만 대상 |
| 점수 합치기 | 문서별 `1/(60+벡터 순위) + 1/(60+키워드 순위)`(걸리지 않은 쪽은 0), 회차 점수 = 그 회차 문서 최고값, 상위 3 회차 |
| 키워드로만 걸린 문서 | 벡터 유사도 0.35 미만이어도 결과에 포함 |
| 기간에 맞는 기록 없음 | `NO_RESULTS`(기간을 빼고 다시 검색하지 않음) |
| 카드 `score` | 공개 응답 모양 유지. 값은 지금처럼 회차 최고 벡터 유사도(키워드로만 걸린 회차는 0.35 미만일 수 있음). 정렬은 RRF 기준 |
| 설명 관련도 재확인 | FN-RET-13은 원문 질문 임베딩 유지. 키워드로만 걸린 카드는 `INSUFFICIENT`가 될 수 있음 |
| 설정 | learning `app.memory.query-rewrite.enabled`(기본 true). false면 변경 전 벡터 단독 검색 |
| DB | learning 스키마 변경 없음(학생당 문서가 적어 필터 뒤 정확 탐색, 새 인덱스·`pg_trgm` 없음). core 마이그레이션 1개(`callType` 확장) |
| 저장·로그 | 질문·변환 결과 미저장, 운영 로그 원문 미기록(NFR-SEC-05) |
| 비용·지연 | 검색 1회당 LLM 약 $0.0001 추가, 지연 1~2초 증가(설계 추정). 실측은 약 $0.0003·3.7~5.5초(16.7). 하루 한도 20회 그대로 |

### 16.4 근거
- RRF: 코사인 유사도와 키워드 일치 수는 단위가 달라 점수끼리 더하면 가산점 크기를 평가셋으로 맞춰야 함. 순위 기반 합치기는 조정값이 k 하나뿐임
- 키워드로만 걸린 문서 포함: 정확한 단어("토끼")가 들어간 기록을 놓치지 않게 함. 반복 결과 문제를 줄이는 것이 이번 변경의 목적임
- 기간 없음 → `NO_RESULTS`: 학생이 말한 기간과 다른 기록을 보여주지 않음. 기존 "관련 결과 없음" 화면 재사용
- 설명 원문 유지: 공개 설명 API·흐름(13장)을 바꾸지 않고 LLM 호출을 늘리지 않음
- ai 7초(처음 4초): ai 기본 LLM 설정(15초·재시도 1회)이면 learning 8초가 끊은 뒤에도 ai가 계속 호출해 사용량만 쌓임. learning보다 1초 짧게 둠

### 16.7 ai 질의 변환 구현 (#681, 2026-11-16)
- `app/memory_query/`로 4.2.7 구현. 키워드 최대 5개·재시도 없음·가짜 구현 규칙은 기준안 그대로

- 질문 속 지시 방어: 구분자 + 꺾쇠 전각 치환 + 시스템 규칙, 결과는 칸 검사로 한 번 더 막음

### 16.8 learning 하이브리드 검색 구현 (#682, 2026-11-16)

- 기준: #693 병합 develop `65acfe15`. 이슈 본문의 초기 5초 대신 16.7에서 확정한 learning 8초·ai 7초를 사용한다.

- 성공 시 검색용 문장을 임베딩하고, 같은 학생·보유 회차·지난 주·READY·완료된 THEME_DAY/THEME_REVIEW 범위에서 벡터와 `content_text` 키워드를 합친다. 키워드의 `!`, `%`, `_`는 문자로 처리한다. 유효한 기간은 회차와 겹치는 반열림 구간으로 제한한다.
- 문서별 RRF(k=60)의 회차 최고값으로 상위 3개를 정렬한다. 응답 모양·상태·카드의 벡터 유사도 점수는 유지한다. 키워드만 일치한 문서도 포함하고, 기간 결과가 없으면 기간을 제거하지 않고 NO_RESULTS를 반환한다. 설명 관련도 재확인은 기존 원문 임베딩 그대로다.
- JDBC 삭제 직후 같은 트랜잭션에서 조회해도 삭제 전 MyBatis 결과를 재사용하지 않도록 하이브리드 조회 캐시를 비운다. 새 테이블·마이그레이션·의존성은 없다. #568의 답변 키워드 기준선도 유지한다.
- 설정: `MEMORY_QUERY_REWRITE_ENABLED=true`(기본), `MEMORY_QUERY_REWRITE_TIMEOUT=8s`. Compose·local/prod learning 배포 값에 반영했다. false로 바꾸고 learning을 재시작하면 기존 원문 벡터 검색으로 돌아간다. 로컬에서 AI 없이 개발하려면 ai의 `MEMORY_QUERY_PROVIDER=fake`를 사용한다(기간 없음·공백 분리 키워드).
- 검증은 별도 임시 PostgreSQL/pgvector와 합성 답변을 사용한다. 기존 로컬 서비스 DB·학생 기록은 수정하지 않는다. 실제 AI 검증도 합성 질문·답변만 전송한다. 검색 정확도의 전체 개선 평가는 #568과 구분한다.

### 18.2 지표·통과 기준

지표는 V·H·K1·K2 모두 같은 식으로 계산하고, 결과서 숫자는 평가용(초5)만 쓴다. 조정용(초3)은 기준값·카드 수 고르기에만 쓴다. 통과 기준은 V와 H(서비스 기본 설정) 둘 다에 적용해 보고한다.

| 지표 | 정의 | 통과 기준 |
|---|---|---|
| 회차 Recall@3 | 결과가 있어야 하는 질문에서 정답 회차가 카드 3개 안에 든 비율(여러 회차 질문은 찾은 정답 비율) | ≥ 0.80 |
| 키워드와 차이 | Recall@3 − max(K1, K2) | ≥ 0.10 (질문 36개라 0.10 미만은 "비슷함"으로 씀) |
| Hit@1·MRR@3 | 1위가 정답인 비율, 첫 정답 순위의 역수 평균(3위 밖 0) | 기준 없음, 같이 보고 |
| 관련 없음 거절률 | 관련 없음·다른 학년 테마·범위 시험 질문 중 `NO_RESULTS` 비율 | ≥ 0.80 |
| 접근 범위 위반 | 모든 질문·방식 결과에 다른 학생·진행 주·`EXTRA`·액자 없는 회차·삭제 학생 시도가 나온 건수 | 0건 |
| 응답 시간 | 내부 API 응답 p50·p95(질문 임베딩 포함, H는 질의 변환 LLM까지 포함, core·브라우저 제외). V는 예열 5회 뒤 질문마다 3회, H는 예열 2회 뒤 1회(LLM 2~5초), 순차 | p95 ≤ 2초 |
| 사용량 | 질문 임베딩 토큰(core `llm_usage` `MEMORY_EMBEDDING`), H 질의 변환 호출·토큰(`MEMORY_QUERY`) | 기준 없음, 조건과 같이 보고 |
| 추억 설명 | 평가용 결과 카드로 설명 20건(실제 LLM, 질의 변환 끔). 담당자가 근거 일치·근거 밖 활동·감정·의도·능력 추정을 표시 | 근거 밖 활동·추정 0건 |

- 기준값(V): 조정용에서 0.10~0.60을 0.01 간격으로 보고 (Recall@3 + 거절률) ÷ 2가 가장 큰 값, 같으면 0.35에 가까운 값을 고른다. 평가용에는 고른 값과 지금 값 0.35를 둘 다 보고한다
- 설명은 질의 변환을 끄고 잰다: 설명 관련도 재확인은 원문 질문 임베딩이라(16.3) 검색 방식과 무관하고, 하이브리드 카드는 0.35 미만일 수 있어 설명 러너의 카드 점수 검사에 걸림
- 질문 수가 적어 Recall·거절률은 Wilson 95% 구간을 같이 적는다
- 기준에 못 미쳐도 기준을 바꾸지 않고 결과와 원인을 결과서에 적는다. 설정 값(`MEMORY_MINIMUM_SIMILARITY`·임베딩 모델) 변경은 결과를 보고 따로 정한다
- 결과 파일은 요약 + 건별(질문 ID·방식·결과 회차 키·점수·시간). 답변·질문 원문은 결과 파일에 넣지 않는다. 학생 답이 든 확인 페이지·설명 표시지·적재 표는 커밋하지 않는다(`.gitignore`)

### 19.2 구현 판단

- **사기는 해금 흐름 재사용**: `LookUnlockService.purchase`가 해금과 같은 순서(학생 행 `FOR SHARE` → 잔액 행 `FOR UPDATE`, 원장 음수, 잔액 차감, `IdempotencyService`)로 처리하고 새 결제 경로는 없다. 같은 키 재전송은 처음 응답(1회 차감), 키가 다르면 새 구매. 원장 UK `(student, UNLOCK, source_key)`는 사건 키에 멱등 키가 들어가 같은 키 이중 기록도 막는다
- **경로를 나눔**: 해금(`unlock`)은 "이미 해금이면 차감 없이 200"이 규칙이라 여러 번 사기와 뜻이 부딪힌다. 방 소품은 `POST /students/me/look-items/{itemKey}/purchase`로 따로 두고, `unlock`에 방 소품을 보내거나 `purchase`에 다른 칸을 보내면 422
- **보유는 구매 행**: `student_room_decor` 1행 = 구매 1번(그 원장 행을 `ledger_id` UK로 가리킴). 개수 칸을 두지 않아 원장과 보유가 1:1로 맞고, 상한 검사는 잔액 행 잠금 아래에서 행 수로 한다
- **놓은 자리는 전체 교체**: `room_decor_spot` PK `(student_id, spot_no)`, CHECK 1~8. `PUT /students/me/room/decor-spots`가 학생 행 `FOR NO KEY UPDATE`(사기의 `FOR SHARE`·삭제 확정과 직렬화) 뒤 보유 개수를 읽어 넘는 배치를 422로 막고 전체를 지우고 넣는다. 액자 슬롯과 달리 learning을 부르지 않아 트랜잭션 하나로 끝난다
- **응답은 칸만 더함**: 학생 아이템 목록에 `ownedCount`(방 소품 보유 개수, 다른 칸 null)와 `createdAt`(관리자 아이템 등록일, 웹 "새로 나왔어요")을 더하고 기존 칸은 그대로. 착용 응답 `equipped`에는 `FLOOR`가 더해진다(기존 일곱 슬롯 그대로)
- **판매 중단**: 이미 가진 방 소품은 목록(`onSale:false`)·놓은 자리에 남고 새로 살 수만 없다. 바닥은 다른 아이템처럼 해금했으면 계속 착용
- **학생 삭제 확정**: `StudentLookService.clear`가 놓은 자리 → 착용 → 보유 → 해금 → 원장 → 잔액 순서로 같은 트랜잭션에서 지운다(보유 행이 원장을 가리켜 원장보다 먼저)
