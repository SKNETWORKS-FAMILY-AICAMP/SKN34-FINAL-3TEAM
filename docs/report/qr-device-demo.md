# 노트북·태블릿 QR 기기 등록 시연

작성: 김재현 · 2026-10-27

## 문제와 변경

기존 QR은 `/student/login?code=…` 주소를 표시했지만, 등록 코드·PIN·기기 목록이 브라우저별 sessionStorage에 있어 다른 기기에서는 등록할 수 없었다. 초기 학생 인증 확인도 `/student/login`으로 다시 이동하면서 QR의 code 쿼리를 지웠다.

`frontend/web`에서 `npm run dev:qr`를 실행하면 Vite 개발 서버(기본 5196)에 공유 기기 목업이 함께 열린다. 학부모가 만든 코드와 PIN을 별도 브라우저·기기에서 조회하고, 등록 → PIN → 학습 홈까지 기존 공개 API 어댑터로 진행한다. 실제 core-service를 구현한 것으로 표시하지 않는다.

## 사용자 흐름

1. 보호자 노트북에서 `http://127.0.0.1:5196` → 시연 계정 로그인 → 자녀 기기·PIN.
2. `demo-only`로 본인 재확인 → 숫자 4~6자리 PIN 설정(예: 4831).
3. 자녀 선택 → 등록 코드 만들기. QR 주소는 가상 어댑터보다 실제 Wi-Fi 어댑터를 우선 제안하고 직접 변경할 수 있다.
4. 같은 Wi-Fi의 태블릿 기본 카메라로 QR을 읽는다. 카메라 권한이나 앱 내 스캐너는 필요하지 않다.
5. 등록 코드를 자동 입력한 화면에서 기기 이름 → 기기 등록하기. 성공 안내와 PIN 화면으로 이어지고 사용한 코드는 주소에서 제거된다.
6. PIN으로 학생 홈 진입. 새로고침 후에도 기기 등록은 유지되며 학생 PIN은 다시 입력한다.
7. 보호자 화면의 기기 목록은 3초 간격으로 갱신된다. 등록 해제하면 해당 기기의 다음 PIN 로그인을 거부한다.

## 구현 경계

- `scripts/device-demo.ts`: 서버 인스턴스별 메모리 저장소. 등록 코드 10분/1회, 기기 90일, PIN 5회 실패 잠금과 보호자 재설정. PIN은 서버에서 salt를 더한 scrypt 해시로만 저장한다.
- `scripts/device-demo-plugin.ts`: `serve` 전용 Vite middleware. 공유 경로는 `/__demo/device`이고 core의 `/api/v1` 프록시와 분리한다. 요청 크기 제한, 동일 Origin 및 전용 헤더 검사, 응답 no-store를 적용한다.
- `src/mocks/sharedDevice.ts`: 기존 브라우저 목업의 보호자 권한·재확인 검사 뒤 공유 서버를 호출한다. 보호자 목업 소유권 키는 별도 임의 값이고 QR에 포함하지 않는다. 서로 다른 보호자 목업의 기기 목록을 분리한다.
- 기기 식별자는 서버의 임의 자격증명을 담은 HttpOnly·SameSite=Strict 쿠키를 사용한다. 공개 deviceId를 자격증명으로 쓰지 않는다. HTTPS에서 실행하면 Secure도 적용한다. 이 쿠키 경로는 `/__demo/device`이고 실제 인증 쿠키와 다르다.
- `src/mocks/sharedRuntime.ts`: LAN HTTP에서도 기존 MSW 핸들러를 `getResponse`로 실행한다. 이 모드에서만 서비스 워커 대신 개발용 fetch 어댑터를 쓴다. 정규 MSW 실행은 그대로 유지한다.
- LAN HTTP에 없는 randomUUID와 Web Locks의 대체 경로는 **개발 + 공유 목업 모드에만** 적용한다. 운영 인증의 Web Locks 요구를 완화하지 않는다.
- `SessionProvider.tsx`: 이미 학생 로그인 페이지에 있으면 다시 이동하지 않아 QR 쿼리와 기존 돌아갈 화면 상태를 보존한다. 이 수정은 실제 API 모드에도 적용한다.
- QR 여백을 4모듈, 표시 크기를 224px로 두고, QR 생성 실패 시 코드 직접 입력을 안내한다. 주소를 변경하는 동안 이전 주소의 QR을 표시하지 않는다.

## 검증

- 단위·계약 테스트 76개 통과(신규 공유 서버 테스트 7개 포함).
- 독립 브라우저 3개로 LAN HTTP 등록·코드 재사용 거부·PIN·새로고침·해제의 5개 시나리오 통과.
- 기존 일반 MSW 학생 기기 브라우저 회귀 11개 통과(QR 쿼리 유지 회귀 추가).
- lint, TypeScript/운영 빌드, QR 플래그를 켠 운영 빌드의 목업 제외 검사 통과.
- 기존 단일 JS 번들의 500kB 초과 안내는 남아 있다. 이번 작업에서 번들 분할은 변경하지 않았다.

자동 검증 결과는 아래 명령으로 재현한다. 실제 태블릿 카메라를 사용한 물리적 스캔과 외부 Wi-Fi·Windows 방화벽 설정은 별도 현장 확인 대상이다. 브라우저 검증은 QR에 넣은 주소를 독립 브라우저에서 여는 방식이다.

```powershell
npm test
npm run lint
npm run build -- --mode qr-demo
node tests/production-mocks.mjs
# 별도 터미널
npm run dev:qr
# Playwright/Chrome 경로를 설정한 검증 터미널
$env:DEMO_URL='http://127.0.0.1:5196'
node tests/qr-device-browser.mjs
# 일반 VITE_API_MOCK=true 서버 주소를 DEMO_URL로 설정한 뒤
node tests/student-device-browser.mjs
```

신규 서버 테스트는 독립 기기의 쿠키·PIN·목록, 동시 QR 재사용, 코드·기기 만료, PIN 잠금·재설정, 다른 보호자 접근 차단, 공개 ID 쿠키 위조 거부, 기기 해제, Origin/헤더 검사, 자녀 연결 해제를 확인한다. 운영 산출물 검사는 공유 목업의 경로·쿠키명·상태·소유권 키가 빌드에 포함되지 않는지 확인한다.

## 한계와 후속

- 운영용 기기 인증 서버나 실제 Google 재인증을 구현한 것은 아니다. 보호자 로그인·재확인은 기존 개발 fixture이며 실제 개인정보를 사용하지 않는다.
- 공유하는 것은 등록 코드·PIN·기기 목록이다. 학습 답변·초안·리포트는 기존 브라우저별 목업 상태이고 기기 간 공유하지 않는다.
- 서버를 재시작하면 공유 상태가 초기화된다. 새 서버 인스턴스에서는 새 보호자 목업 키를 발급하고, 이전 기기 쿠키는 거부한다.
- 앱을 이미 열고 있는 학생의 access 세션까지 즉시 강제 종료하는 기능은 포함하지 않는다. 해제 후 다음 PIN 로그인은 차단한다.
- LAN 시연은 같은 네트워크에서 해당 포트 접근이 가능해야 한다. 공개 터널·외부 배포·방화벽 규칙 자동 변경은 추가하지 않았다.
- 실제 #58 API가 준비되면 기본 `npm run dev`의 API 모드에서 연결한다. 전용 `dev:qr`는 계속 명시적 개발 시연 모드로 남긴다.

작업은 `feature/qr-device-demo`에 있다. 2026-10-28 사용자 요청으로 이 브랜치의 커밋·push·PR 생성을 진행한다. #104는 이미 develop에 병합되어 있으며, 대상 브랜치는 사용자 확인 후 PR에 기록한다. 현재 검증은 QR 브랜치 단독 기준이며 #104 이후 통합 검증 결과로 표시하지 않는다.
