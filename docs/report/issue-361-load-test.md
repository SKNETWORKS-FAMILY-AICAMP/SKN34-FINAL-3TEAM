# #361 AWS 데모 core·NAT 1차 부하 시험

## 1. 목적과 결론

AWS 데모(CloudFront → ALB → core)에 k6로 단계별 부하를 주어, core와 NAT 가운데 무엇이 먼저 한계에 닿는지 확인했다.
이 시험은 #211(Karpenter·HPA) 적용 전에 하는 1차 시험이다. 2차는 #211 적용 뒤, 3차는 이중화 작업 뒤에 같은 방식으로 반복한다.

**결론 (계정 1개, 판정 동시 15건 고정 조건)**

1. **먼저 한계에 닿은 것은 DB 계층이다.**
   - RDS(db.t4g.small) CPU가 VU에 거의 비례해 올랐다: 100명 24% → 200명 46% → 300명 68%.
     이 추세면 약 350명에서 중단 기준 80%에 닿는다.
   - 같은 300명 단계에서 core Hikari 풀(10)이 사용 9, 대기 요청 8까지 찼다.
2. **core CPU는 그다음이다.** 300명에서 최대 0.69코어(한도 1)였고, 약 400명에서 한도에 닿을 것으로 추정한다.
3. **NAT는 core·DB보다 훨씬 나중에 한계에 닿는다(계산 판단, 실측 아님).**
   - LLM을 클러스터 안 스텁으로 대체해 이번 시험에서는 NAT 경유 트래픽이 거의 없었다. 300명에서 활성 연결 4개, 포트 할당 오류 0이었다.
   - 실제 LLM을 썼다고 가정한 300명 트래픽도 NAT 한도의 1% 미만으로 계산된다(4.1절). NAT 실측은 2차 시험에서 한다.
4. 300명까지 API 오류율 0%(0/40,312), API p95 374ms였다. 자동 중단 기준에도, 수동 중단 기준에도 걸리지 않았다.
   Pod 재시작은 0회, RabbitMQ 적체도 0이었다.
5. 가상 스레드 pinning: `-Djdk.tracePinnedThreads=short`를 적용한 동안(300명까지) core 로그에 pinning 기록(`<== monitors`)이 0건이었다.

### 시나리오

VU를 비율대로 나누고, 단계마다 올리기 30초, 유지 5분, 내리기 10초로 돌렸다.

| 이름 | 비중 | 흐름 |
|---|---|---|
| browse | 55% | 보호자 `/me`·리포트 목록·상세·알림·대화 목록, 학생 미션 목록·상세·홈·학습 기록. 요청 사이 1~3초 |
| learn | 20% | 시도 시작 → 첫 답변 → 판정 SSE 완료 → 마무리 → 돌아보기. 미션은 서술형·에세이·풀이 과정형 5개 |
| notify | 15% | 알림 SSE를 120초 붙잡고 다시 연결 |
| analyze | 10% | 분석 대화 생성 → 질문 SSE를 결과까지 → 30~60초 생각 |

자동 중단 기준은 두 가지다. API(`kind:api`) 오류율이 1%를 넘거나, p95가 1초를 넘으면 1분 뒤부터 k6가 멈춘다.
300명 단계에서는 RDS CPU를 1분마다 감시해 80% 이상이면 k6 REST API로 멈추게 했다. 실제로 걸린 적은 없다.

## 4. 판정 동시성 한계 (계정 1개)

보호자 로그인은 구글 OAuth뿐이라 시험 계정을 더 만들 수 없었다. 보호자당 자녀는 최대 3명이다.
시도는 자녀×미션마다 하나만 진행되므로, 학습 칸은 3 × 5 = **15개**로 고정됐다.

| 총 VU | 학습 VU | 칸당 VU | 판정 처리량 상한 |
|---|---|---|---|
| 50 | 10 | 0.7 | 실측 0.9건/초 |
| 75 | 15 | 1.0 | 약 1.4건/초 |
| 100 | 20 | 1.3 | 1.4건/초 (실측 461건/5.5분 ≈ 1.40) |
| 300 | 60 | 4.0 | 1.4건/초 (실측 480건) |

- 학습 한 바퀴는 VU 하나당 약 11초다(판정 SSE 7.5초 + 생각 시간 + 제출·마무리). 따라서 판정 처리량 상한은 15 ÷ 11 ≈ 1.36건/초다. 75명을 넘으면 LLM·채점·RabbitMQ 쪽 부하는 더 늘지 않는다.
- 칸을 얻지 못한 학습 VU는 경합(`learn_conflict`)으로 집계된다.
  - 이들은 새 LLM 호출을 만들지 않는다.
  - 대신 시도 시작 → (판정 중이면) 같은 답변의 SSE 이어 받기 → 마무리·돌아보기 API를 반복한다.
  - 마무리 응답은 `409 REVEAL_CONDITION_UNMET`(300명에서 2,798건)과 `ATTEMPT_CLOSED`(461건)이고, 오류율에서 뺀다.
- **해석상 주의:** 200명과 300명의 `student_attempts` 지연, learning 스레드 증가(59 → 116), RDS CPU에는 경합 호출이 섞여 있다. 300명 기준으로 API 약 15,000건(약 35%)이 경합에서 생겼다.
  실제 사용자 300명이라면 경합이 없어 이 부분은 줄어든다. 반면 판정 쓰기는 4배 가까이 늘어난다. 따라서 "DB가 먼저"라는 결론은 2차 시험에서 계정을 늘려 다시 확인한다.
- 판정 경로까지 보려면 계정 수 × 15 ≥ 0.2 × VU가 필요하다. 100명은 계정 2개, 200명은 3개, 300명은 4개다.
- VU 300명은 실제 동시 사용자 300명과 다르다. 생각 시간이 1~3초로 짧은 공격적인 사용자라 300명이 초당 약 197건을 보냈다.

### 4.1 NAT 판단 (계산)

[#212 점검](issue-185-aws.md#s3-gateway-엔드포인트와-nat-병목-점검-212-2026-11-04)에 따르면 pod 사이 호출과 RDS는 VPC 내부라 NAT를 거치지 않는다.
S3(ECR 레이어 포함)도 Gateway 엔드포인트로 빠진다. NAT를 거치는 것은 외부 호출뿐이고, 부하에 비례하는 것은 LLM 호출이다(판정·되묻기·분석·리포트 서술).
결제·OAuth·Secret 갱신은 사용자 행동 빈도가 낮아 이 계산에서 뺐다.

| 항목 | 300명, 계정 제약이 없는 경우의 추정 | NAT Gateway 한도 | 비율 |
|---|---|---|---|
| LLM 호출 수 | 판정 60 VU ÷ 11초 ≈ 5.5건/초 + 분석 약 0.7건/초 ≈ **6건/초** | — | — |
| 동시 연결 | 호출당 응답 5~8초 유지 → 약 50개 (판정에 되묻기 생성이 붙어도 100개 이하) | 목적지당 동시 연결 55,000개 | 0.2% 이하 |
| 대역폭 | 요청·응답 합계 호출당 수십 KB → 1Mbps 미만 | 기본 5Gbps(최대 100Gbps로 자동 확장) | 0.1% 미만 |
| 포트 할당 오류 | 1차 시험 전 단계 0 | — | — |

- 같은 300명에서 RDS는 68%, core 풀은 포화 직전이었다. NAT는 그보다 몇 자릿수 여유가 크다.
- NAT의 남은 위험은 성능이 아니라 가용성이다(2a 단일 NAT, #212 결론과 같음).
- 실측은 2차 시험에서 실제 LLM 또는 클러스터 밖 스텁으로 NAT를 거치게 해 `ActiveConnectionCount`·`ErrorPortAllocation`·`BytesOutToDestination`을 다시 본다.

## 6. 진행 중 발견한 문제

- **토스 공용 위젯 키 실패:** 데모는 토스 문서 공용 테스트 키를 쓴다. 이 키로 `api.tosspayments.com/v1/payment-widget/widget-groups/keys`가 모든 origin과 variant에서 500(code 5000)을 돌려줘 결제할 수 없었다. kind에서는 11/03에 정상이었으므로 토스 쪽 문제로 보인다. 팀 전용 테스트 키로 바꿀지 검토가 필요하다.
  그래서 PREMIUM 상품을 켰다가 다시 끄고, 결제 없는 시험 구독을 넣어 유료 경로를 시험했다(7장).
- **OTel span 전송 404:** core가 Collector로 span을 보낼 때 404 경고가 난다. 시험과는 무관하며 별도로 확인할 대상이다.
- **k6 스크립트에서 고친 점:**
  - 학생 로그인 `Origin` 헤더 누락으로 403이 났다.
  - Spring SSE 이벤트 구분(`event:` 뒤 공백 없음)을 잘못 처리했다.
  - 학년별 미션 차이(`MISSION_NOT_AVAILABLE`) 때문에 자녀별로 미션 목록을 따로 받게 했다.
  - 기록 비공개 자녀(`STUDENT_RECORDS_PRIVATE`)는 대화 목록 조회에서 뺐다.
  - 학습 칸 배정이 겹쳐서, 경합을 만나면 다음 칸으로 옮기게 했다.
  - 10명·25명 값은 이 수정 뒤 round3에서 다시 측정한 값이다.
