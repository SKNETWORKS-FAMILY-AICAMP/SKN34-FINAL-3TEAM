## 5. 설계 판단

- 포인트 적립에 새 메시지를 두지 않음: learning은 발행 없음(아키텍처 1.6)이고, 적립 사건(학습 완료·공유·반응·되돌아보기 열람)은 모두 core가 learning 응답을 프록시하는 경로에서 확인할 수 있다
- 일일 리포트를 별도 테이블이 아니라 `period_type`으로 일반화: 작업·재처리·Outbox·알림·다운로드 경로를 그대로 쓰기 위해서다. 이 때문에 정기 생성 부분 UK에 `period_type`을 넣어야 한다(월요일 일일·주간 작업의 `period_from`이 같을 수 있음)
- 작성자 별명은 core가 붙임: 별명·꾸미기는 core 소유이고, 다른 학생에게 학생 ID를 노출하지 않기 위해 core가 응답에서 지운다
- (2026-11-07 본문 통합 때 실제 DB·메시지 계약과 대조해 바꾼 설계)
  - report `weekly_report` 재생성 UK·revision 잠금에 `period_type` 추가: 월요일 일일·주간 리포트의 `period_from`이 같아 기존 UK `(student_id, period_from, revision)`가 충돌
  - core `conversation.report_id`·`report_revision` 추가: "리포트 판 고정"을 다음 메시지에서도 알아야 함. core가 메시지마다 그 판을 읽어 ai에 넘겨 ai → report 새 의존을 만들지 않음
  - 포인트 원장 사건 키를 uuid `source_id`에서 문자열 `source_key`로: 되돌아보기·완주(주 단위)·반응(복합 키)은 uuid가 없음
  - 공유물을 시도당 1개에서 학생·미션당 1개로: 다시 풀기마다 같은 학생 글·공유 포인트가 늘고, 받은 반응이 다른 답에 붙는 문제 방지
  - 새 NOT NULL 컬럼은 기본값 없이 준비·최종 마이그레이션으로 나눔: 검증 스크립트가 컬럼 기본값을 금지(`parent_sharing_enabled`만 예외)
  - 무료 하루 1개 집계는 core 새 테이블 `mission_daily_usage`(시도 ID PK): core는 learning 시도를 직접 볼 수 없고, #210 결정대로 Redis 없이 PostgreSQL로 셈
