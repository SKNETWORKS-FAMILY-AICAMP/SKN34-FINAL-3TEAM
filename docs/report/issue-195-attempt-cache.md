# 시도 상세 HTTP 캐시와 돌아보기 전환 (#195)

## 재현과 원인

#35 M1의 실제 Chrome·MSW OFF 검증(b35b22e)에서 답변 제출·판정·마무리는 저장됐지만 웹은 이전 시도 상세를 사용해 돌아보기 입력으로 진행하지 못했다. learning 상세에는 `finishedAt`·정답·체크리스트가 있고, 초안 ETag가 `"2"`인 조건부 GET에는 304가 재현됐다.

초안 버전은 피드백·마무리·돌아보기 상태의 버전이 아니다. 이를 상세 표현의 HTTP 캐시 검증자로 사용하면 상태 변경을 놓친다.

## 변경

- core 공개 `GET /attempts/{attemptId}`에만 `Cache-Control: no-store`를 설정한다.
- 웹 상세 조회와 답변 제출·마무리·돌아보기 후 재조회는 `cache: 'no-store'`를 사용해 이미 저장된 응답도 재사용하지 않는다.
- learning 업무 로직과 초안 ETag/If-Match·409 계약, 다른 조회의 캐시 정책은 변경하지 않는다.
- 호출 경로: 웹 게이트웨이 → core LearningController → LearningProxyService → learning 시도 상세. 응답은 core에서 저장 금지를 지정하고 웹은 최신 본문을 화면 상태로 반영한다.

## 검증

- 기준: develop `94bf3ea`, 2026-10-31 로컬 검증.
- JDK 21 컨테이너에서 `LearningProxyIntegrationTest` 14개, `LearningClientTest` 5개 통과(실패·오류·생략 0), `bootJar` 성공. core 인증·필터·PostgreSQL은 실제 구현, learning은 HTTP 대역이다. core 전체 테스트 실행 결과는 아니다.
- 웹 전체 테스트 144개, lint·build·`production-mocks.mjs` 통과. 기존 `AdminOperations.tsx` immutability 경고 1건과 500kB 번들 경고는 남아 있다.
- 신규 웹 회귀는 초안 ETag가 유지되는 오래된 상세 응답을 재사용하는 대역을 두고 상세·제출 후·마무리 후·돌아보기 후 조회가 최신 상태를 받는지 검사한다.
- 실제 Chrome·MSW OFF·수정 core JAR·실제 learning/PostgreSQL/Redis/RabbitMQ로 아래 흐름을 확인했다.

### 실제 브라우저 결과

1. 기존 실패 시도 `54c15667-0226-4913-aea2-d7d39cc28ebe`에 학부모 동석 세션으로 재진입: 정답·체크리스트·돌아보기 폼 표시, 돌아보기 저장 후 DB와 공책 `COMPLETED` 확인.
2. 실제 Google 재인증 → 사용자 PIN 설정 → 등록 기기 PIN 로그인 성공. 기기 `last_used_at` 갱신도 확인했다.
3. PIN 학생 세션에서 새 시도 `25bd2494-a7e1-4041-bb57-e906e53dfda9` 시작 → 초안 저장 → 답변 제출 → 규칙 정답 판정 → 마무리 → 돌아보기 저장까지 완료했다. 마무리 직후 페이지 재진입 없이 정답·체크리스트·돌아보기 버튼이 표시됐다.
4. 실제 Google 보호자 재로그인 후 대시보드에 학습 2건·완료 2건, 두 돌아보기 기록이 반영됐다.

가상 자녀와 자체 제작 선택형 문항을 사용했다. 이 검증은 실제 OAuth·PIN·미션 저장 경로이며 LLM 판정·실결제·배포 검증은 아니다. 학생에서 보호자로 이동할 때 로그인 페이지를 새로 열어 재로그인했으므로, PIN 로그아웃 후 보호자 로그인 버튼 자체의 전환과 로그인 중인 보호자 세션 유지 여부는 이번 통과 범위에 포함하지 않는다. 이전 #35 검증의 분석·리포트 결과를 새 기준 전체 재검증으로 표현하지 않는다.

## Google 재인증 설정 (#196)

기존 OAuth 클라이언트의 승인된 리디렉션 URI에는 일반 로그인 콜백만 있었다. 사용자 승인 후 동일 origin의 `/api/v1/auth/google/reauth/callback`을 추가하고, 설정을 다시 열어 두 URI가 저장됐음을 확인했다. 실제 Google 재인증은 `VERIFIED`로 완료됐고, 원래 보호자 화면에서 재확인 토큰 수령 후 사용자가 검증용 PIN을 설정했다. PIN 로그인·미션 완료는 위 실제 브라우저 검증에서 확인했다. 비밀 키·PIN·토큰은 문서에 기록하지 않는다.
