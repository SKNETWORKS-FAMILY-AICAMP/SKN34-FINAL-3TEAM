# app-service chart (#171)

One Helm release owns one Deployment and, where needed, a ClusterIP Service, HPA or KEDA ScaledObject, PDB, Ingress, NetworkPolicy, and a versioned migration Job. The six local releases use the values in `../../environments/local/`. The runtime commands and ports are the existing Dockerfile and Compose commands.

## Inputs and ownership

- Set `image.repository` with `image.tag` or immutable `image.digest`. Local `:local` images must be built and loaded into the `sagomungchi-local` kind cluster before sync. #186 publishes GHCR/ECR images and updates deployable tags or digests. The values do not imply published images.
- All releases target namespace `app`. The sole namespace-wide deny policy belongs to the core release; every app release also owns its narrower allow policy. The local Ingress exposes only core's `/api` path through class `nginx`.
- The `app/app-service-credentials` Secret is a prerequisite and is not created by this chart. Kubernetes cannot read a Secret from the `platform` namespace. Prepare the app namespace Secret from the same authorized source as the platform credentials, without checking values into Git or changing `platform/platform-data-credentials`.
- In the local `sagomungchi-local` cluster, `infrastructure/kind/create-app-secrets.ps1` prepares the app Secret (and the observability Secret when Grafana keys are set) from the repository root `.env` after checking the fixed context and node identity. `create-platform-secret.ps1` prepares the platform Secret from the same file.
- Required keys: `CORE_DB_USERNAME`/`CORE_DB_PASSWORD` and `LEARNING_DB_USERNAME`/`LEARNING_DB_PASSWORD` (app DML roles), `CORE_MIGRATE_USERNAME`/`CORE_MIGRATE_PASSWORD` and `LEARNING_MIGRATE_USERNAME`/`LEARNING_MIGRATE_PASSWORD` (Flyway DDL roles, #230), `RABBITMQ_USERNAME`, `RABBITMQ_PASSWORD`, `RABBITMQ_URL` (URL-encoded AMQP credentials), `INTERNAL_TOKEN`, `AUTH_JWT_SECRET`, `REPORT_DATABASE_URL`, `REPORT_ALEMBIC_DATABASE_URL`, `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD`. `OPENAI_API_KEY` is optional for Pod startup but AI LLM calls fail without a configured provider and key. Other optional keys (#236), copied from `.env` only when set: `ANTHROPIC_API_KEY`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `PAYMENT_FREE_PRODUCT_ID`, `PAYMENT_BILLING_ENCRYPTION_KEY`, and the `TOSS_TEST_*`/`TOSSPAYMENTS_SECRET_KEY` test keys. Core starts without them, but Google login, payments and billing fail until they are set. Local `REPORT_DATABASE_URL` uses the `report_app` role and `REPORT_ALEMBIC_DATABASE_URL` the `report_migrate` role, both on the `report_db` database at `postgres.platform.svc.cluster.local`; the Alembic-only key doubles each URL-encoded `%` for its existing ConfigParser path. The report API and worker continue using the regular URL.
- The local report API signs download URLs for `http://127.0.0.1:19000`. To exercise a URL from the host, explicitly port-forward the local cluster's `platform/minio` Service from host port 19000 to service port 9000 while testing. This is a local test endpoint, not an EKS public storage URL.
- The platform Secret, RabbitMQ definitions, PostgreSQL databases, MinIO buckets, and PVCs stay under `platform-data` ownership. This chart neither creates nor mutates them. Platform namespace ingress deny and observability network policy remain separate work.
- For core and learning, `javaAgent.enabled` copies the pinned official OpenTelemetry Java agent JAR with an initContainer, then sets `JAVA_TOOL_OPTIONS` only in the chart. A `JAVA_TOOL_OPTIONS` entry in `env` is merged after the agent flag instead of replacing it (#187; prod sets `-XX:MaxRAMPercentage=60.0`). `tracing.enabled` (#187) switches the agent to `OTEL_TRACES_EXPORTER=otlp`; services without the agent get the same `OTEL_*` values for their own SDK setup (report-worker). It needs `networkPolicy.egressToCollector` and the observability `tempo.enabled` backend. Their existing Gradle and application files are untouched. Local values export **metrics only** to Collector 4318; traces and logs are off because no trace backend is configured locally. The added image, startup work and JVM memory use require runtime measurement before production use.
- The AI image includes opt-in Langfuse v4 instrumentation. Keep `LANGFUSE_ENABLED=false` in local values while the Langfuse backend is unavailable. To enable it in an environment, set `LANGFUSE_ENABLED=true`, supply `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY` from an app namespace Secret, set `LANGFUSE_OTLP_ENDPOINT` to the Collector's full OTLP/HTTP `/v1/traces` URL, and set `networkPolicy.egressToCollector=true`. The Collector trace pipeline and authenticated Langfuse exporter must also be enabled in that environment. The AI SDK records call type, prompt version, model, token counts and error code; it does not pass prompt text, answer text or student identifiers to observations. Missing keys or endpoint fail startup when enabled.

## Migration and scaling

- The core and learning Flyway Dockerfiles in `../../migrations/` copy the service's existing SQL into a dedicated image. Their local image tags and the report Alembic image must match the app revision. `migration.revision` changes only when migration files change. A PreSync NetworkPolicy at wave -2 permits DB access before the PreSync Job at wave -1, including later syncs under app default deny. The named Job is retained after success; the chart does not run migrations at application startup or automatically downgrade a database. `migration.extraVolumes`/`extraVolumeMounts` add Job-only volumes such as the RDS CA ConfigMap; the app's `extraVolumes` are not shared.
- `report-api` uses the report image's normal Uvicorn entrypoint and always keeps at least one replica. `report-worker` uses `python -m app.worker`, consumes `report.report.generate` and `report.student.deleted`, and has KEDA 0–1 with prefetch 1 in local values. Increase the maximum only after measuring LLM request capacity.
- KEDA triggers are `keda.queues` (RabbitMQ, needs the TriggerAuthentication secret) and/or `keda.cron` time windows (#476). `keda.renderReplicaCount` keeps `replicas: replicaCount` in the Deployment so a scale-to-zero workload is installed at 0 instead of the Deployment default 1; a helm upgrade inside an active window resets it until KEDA's next poll.
- `modelDownload` (#476) adds an initContainer that writes a model into an emptyDir at `mountPath` (read-only in the app container); its command, args and env choose MinIO (local) or S3 with Pod Identity (prod). `nodeSelector` and `tolerations` pin a workload to a dedicated NodePool. The `sllm-server` release uses all three; locally it runs the `infrastructure/stubs/llm-stub` image as `sagomungchi/llm-stub:local` instead of a real model.
- `affinity` is passed to the Pod spec as is (#372). The AWS demo uses a preferred node affinity to the fixed `application` nodegroup on core, learning and AI so that HPA scale-down removes the newer Pods on Karpenter nodes first. Changing it rolls the Deployment.
- Local HPA and PDB are disabled for single-replica resource checks. The templates support the product deployment target, but metrics-server, capacity and multi-replica behavior need separate verification. Do not use both HPA and KEDA on one Deployment.
- Core's local 15-second preStop and 180-second termination grace are starting values against its existing SSE executor/timer budget. Verify the rolling termination path before treating these as sufficient.

## Current verification boundary

Apply these values to the `sagomungchi-local` kind cluster with explicit Kubernetes context, releases and namespace. The platform-data PVCs and Secret in that cluster stay under `platform-data` ownership. Local core and AI values allow egress to public IPv4 on TCP 443 only (private, CGNAT, link-local and loopback ranges excluded) for Google OAuth, Toss and the LLM API (#236). Calico OSS cannot restrict by FQDN; production egress is decided with #185. A successful chart render does not demonstrate readiness, HPA/KEDA behavior, telemetry ingestion or an end-to-end request.
